# PDF Free — macOS 原生 PDF 阅读器

Swift + PDFKit + SwiftUI，单窗口多标签，追求原生性能最优。

> App 显示名是 **PDF Free**（`Info.plist` 里的 `CFBundleDisplayName` + `CFBundleName`），
> 而产物名保持 `PDFReader` / `com.jiejie.pdfreader` 不变 —— 改名只动用户看到的那一层。
> 图标由 `tools/make_app_icon.py` 用代码画出来（可复现、可改配色）。

### v1.3.8 — 涂鸦"越画越卡"与箭头三角标定

杰哥反馈：「还是不太跟手，有延迟，涂鸦和图案绘制都有；箭头的三角形位置还不太对」。

#### 一、把延迟量到点子上（探针 + 真窗口 + 合成事件）

上一版只量到"24 个事件"的短拖动 —— 那个长度下三种工具都是 0.1~0.3 ms，看不出问题。
**把点数拉到 900 才现原形**（事件按 8 ms 一拍投递，模拟 125 Hz 鼠标）：

| 笔迹点数 | 每事件处理器耗时 | 事件滞后 P90 | 滞后峰值 |
|---------|----------------|-------------|---------|
| 24      | 0.57 ms        | 0.1 ms      | 0.6 ms  |
| 300     | 0.39 ms        | 4.6 ms      | 8.7 ms  |
| 900     | **1.09 ms**    | **40 ms**   | **80 ms** |
| 1800    | 1.56 ms        | **117 ms**  | **253 ms** |

**滞后随笔画长度线性增长** —— 这就是"越画越不跟手"。

根因不是渲染，是 **`redrawInk`：每来一个点就重建整条笔迹**
（`annotation.remove(path)` 掉每一段 + 重新 `add` + 改 `bounds`）。成本 O(点数)，
而它落在**每一次鼠标事件**里。

排除过程（每项都是实测，而不是推测）：

| 关掉什么 | 900 点滞后 P90 |
|---------|---------------|
| 什么都不关（现状） | 40 ms |
| 关掉页面画布上的草稿绘制 | 39 ms（不是它） |
| 关掉图层预览 | 39 ms（不是它） |
| 两个都关 | 36 ms（都不是） |
| **关掉「每事件改 PDFAnnotation」** | **8 ms** ← 就是它 |

#### 二、改法：拖动期间一个字都不写进 PDFAnnotation

涂鸦拖动时**只 `append` 点**，预览几何由 `AnnotationRenderer.inkPaths(points:lineWidth:)`
直接按点构建；笔迹落成批注推迟到 `finishDrawing` 做一次（`buildInkPath`）。
形状类本来就是 O(1) 变更（只改 bounds 和两个端点），不受影响。

顺手把**拖动期间的 `needsDisplay = true` 也去掉**了 —— 预览完全由 `CAShapeLayer` 承担，
不需要 PDFKit 再合成一遍整页（实测 `drawPagePost` 调用从 448 次降到 46 次）。
`drawPagePost` 里那段"画草稿"降级为真·兜底：只在预览图层没挂上时才生效。

修复后：

| 工具 | 900 点 | 1800 点 |
|------|--------|---------|
| 涂鸦 | 8.0 ms（原 **80**） | 26 ms（原 **253**） |
| 矩形 | 6.3 ms | 12.7 ms |
| 箭头 | 8.3 ms | 16.8 ms |

涂鸦从"最差"变成与形状同级，且不再随长度增长。

#### 三、箭头三角形按 PDFKit 实测重标定

做法：让 PDFKit 自己画带 `.closedArrow` 的 Line 批注，栅格化后按「沿线 / 垂直」投影，
量出箭头的可见轮廓：

| 线宽 | 可见头长 | 可见半宽 | 尖端超出端点 |
|------|---------|---------|-------------|
| 2    | 8.8     | 3.8     | 1.6         |
| 3    | 13.6    | 6.5     | 2.9         |
| 5    | 22.9    | 11.0    | 5.1         |
| 8    | 36.0    | 18.1    | 8.3         |

三条规律：**头长 ≈ 4.6×线宽**、**半宽 ≈ 2.25×线宽**、**尖端在端点外 ≈ 1×线宽**
（最后一条是因为 PDFKit 把三角「填充 + 描边」，60° 尖角用 miter 接合会外扩 `(线宽/2)/sin30° = 线宽`）。

旧版用 `max(8, 线宽×4)` 和 25.7° 张角 —— 线宽 3 时只有 12 长 / 9.4 宽，**比 PDFKit 小一圈**，
看着就像"三角没到位"。改成按实测的三个数建纯填充三角后，可见轮廓与 PDFKit 一致
（线宽 3 实测：我们 13.25/6.28/2.55，PDFKit 13.25/6.28/2.55）。

| 功能 | 状态 | 说明 |
|------|------|------|
| **涂鸦拖动不再随长度变卡** | ✅ | 900 点事件滞后 80 ms → **8 ms**，1800 点 253 ms → **26 ms** |
| 拖动期间不再整页重绘 | ✅ | 预览全交给 `CAShapeLayer`；`drawPagePost` 调用 448 → 46 次 |
| **箭头三角与 PDFKit 对齐** | ✅ | 头长/半宽/尖端外扩三项均按实测标定 |
| **第二笔"松手才显示"** | ✅ | 预览层改用 `zPosition` 定序 —— PDFKit 重排图层时会把页面内容层排到我们上面 |
| **点「编辑」就带出右侧栏** | ✅ | 避免第一笔画完才弹栏 → PDFView 变窄 → `autoScales` 重新适配（168%→125%）导致页面跳变 |

#### 四、第二笔只有松手才显示：预览层被 PDFKit 的页面层盖住了

现象：第一笔很跟手，**第二笔画的过程中屏幕上什么都没有，只有松开鼠标才出现结果**。

探针（连画两笔）读出来的证据 —— 注意图层状态是"正常"的，问题在**层级顺序**：

| 时刻 | `pdfView.layer.sublayers` | 结果 |
|------|--------------------------|------|
| 第一笔 | `[页面内容层, 填充层, 描边层]` | 预览在最上面 ✅ |
| 第二笔 | `[填充层, 描边层, 页面内容层]` | **被页面内容层盖住** ❌ |

中间发生了什么：第一笔画完 → `select` → 右侧属性栏弹出 → PDFView 变窄 →
`autoScales` 重新适配 → **PDFKit 重排自己的图层，把页面内容层放到了最后**。
两个预览层还在、`isHidden` 也是 false、`path` 也对，只是**被压在下面**了。

> 这一条和第四点成因相同：**都是"画完第一笔右侧栏才弹"引起的连锁反应。**

**改法**：不靠"加进去的先后"定序，改用 `zPosition`（`1000` / `1001`，页面内容层是 `0`），
PDFKit 怎么重排都盖不住。

对照验证（探针里手动把页面内容层挪到数组末尾来模拟重排）：

| 条件 | 第二笔在像素上 |
|------|--------------|
| 无 `zPosition`（旧） | ❌ **完全不可见**（图层状态却一切正常） |
| 有 `zPosition`（新） | ✅ 可见 |

#### 五、点「编辑」就把右侧栏带出来

`isEditable` 置为 true 时顺手 `revealRightPanel()`。这样栏位在动笔前就占好，
PDFView 的宽度稳定，第一笔画完不会再"页面跳一下"。

#### 七、矩形/圆"起笔跟不动" + 折返拖动的残影

杰哥反馈：「画矩形圆圈时最开始的几个移动点还是没有真正画出来；
拖动时先向右下拖再向左上拖（不松手），两个对称的矩形看得出不是连着的，中间有缝隙。」

**（1）折返拖动出现两个矩形 —— 页面画布上留了残影**

上一版在 `drawPagePost` 里留了一段"兜底"：预览图层不可用时把草稿画进页面画布。
**这段兜底是有害的。**

PDFKit 在布局变化时会重建 `pdfView.layer` 的 sublayers，把我们的预览层挤掉
（`superlayer` 变 nil，下一次 `syncDraftPreview` 才重新挂上）。就在这个空档里，
兜底会把草稿画进页面画布 —— 而**页面画布只在真正重绘时才更新**。
图层重新挂上后显示当前形状，画布上却留着那一刻的旧形状：两个形状同时挂在屏幕上，
缝隙就是"旧形状"和"新形状"之间的差。松手重绘一次残影才消失。

**确定性验证**（不依赖 PDFKit 的重绘时机：把预览层摘掉后直接调 `drawPagePost`，
看画布上有没有被画上东西）：

| 版本 | 画布上的红像素 |
|------|--------------|
| 有兜底（旧） | **432 / 504** ← 残影来源 |
| 无兜底（新） | **0** ✅ |

改法：删掉那段兜底，草稿**只**由独立图层显示，一处都不多画。

> 附带一条实测：折返拖动时，扫描线穿过矩形轮廓的红色段数 = `[2, 2, 2]` ——
> 只有一个矩形，没有残影。

**（2）起笔那几个点"跟不动"：描边内缩 + 我上一轮加的"最小厚度"**

这一版是两处叠加造成的：

- 矩形/圆原来把描边**压在 `bounds` 内侧**（内缩线宽的一半，照抄 PDFKit）。
  框小于线宽时内缩把路径缩成 0；上一轮我给它加了下限，但下限意味着
  **框在长、画出来的形状却几乎不动**。
- 上一轮又为了防止"零厚度 Rect"，把框按**一个线宽**补厚 ——
  正好又把最初的这一段撑住。

细步长慢拖实测（每步 1 个页面点）：

| 拖动 | 修好前 path 尺寸 | 修好后 path 尺寸 |
|------|----------------|----------------|
| 1 点 | 3.8（不变） | **1.25** |
| 2 点 | 3.8（不变） | **2.51** |
| 3 点 | 3.8（不变） | **3.76** |
| 4 点 | 3.8 | **5.02** |

修好后每 1 个页面点 = 1.25 个视图点，**1:1 跟随**；红像素数也单调增长
（90 → 153 → 215 → 309 → …→ 950）。

改法：

- 矩形/圆**不再内缩**，就画在 `bounds` 上 —— 拖多大就是多大。
  代价是描边外缘比 `bounds` 多出半个线宽（常见线宽 1.5~4 点），
  与 PDFKit 的画法差这一点点，肉眼看不出来，换来的是"画得跟手"。
- 厚度只补 **0.5 点**（只为了不让 `Rect` 退化成零厚度），不再动形状本身。

#### 六、短/扁平箭头被当成误触丢掉了

> 本节前半（内缩加下限）已被第七节取代 —— 现在干脆不内缩了；
> 但**箭头按线长判误触**这条仍然有效。

杰哥反馈：「画笔比画矩形圆圈箭头更好用；矩形圆圈箭头最开始拖动的一小段不会立马画出图案，
最好从点击开始就画；还有箭头距离很短时会消失，画不出来。」

**（1）矩形/圆的路径会被描边内缩缩成 0**

矩形/圆的描边**压在 `bounds` 内侧**（内缩线宽的一半，和 PDFKit 一致）。
但框还没拉开到线宽时，内缩把路径直接缩成 0 —— 屏幕上什么都没有。
细步长慢拖实测（读预览图层的 `path.boundingBox`）：

| 拖动距离 | 框 | 内缩后路径 | 屏幕 |
|---------|----|-----------|------|
| 3 点 | 3.8×3.8 | **0×0（bbox 是 inf）** | **什么都没有** |
| 6 点 | 7.5×7.5 | 3.8×3.8 | 有了 |
| 9 点 | 11.3×11.3 | 7.5×7.5 | 有了 |

**画笔和箭头没有内缩，所以从第一个像素就能看见 —— 这就是"画笔更顺手"的来源。**

改法：内缩量按「最多缩到剩 1 点」截断，框越小内缩越少；框正常大时仍是线宽的一半（观感不变）。
另外「刚按下、框还是 0×0」时画一个圆点，跟画笔"点一下留个点"一致，做到**从点击开始就有反馈**。

> ⚠️ 这条"带下限的内缩"**后来又被推翻**（见第七节）：下限意味着框在长、形状却几乎不动。
> 现在是**完全不内缩**，形状 1:1 跟着手走。

> 附带一个坑：空 `CGPath` 的 `boundingBox` 是 `CGRect.null`（`inf`），
> 探针里 `Int(bbox.minX)` 直接被这一下 SIGTRAP 干掉了 —— 格式化几何数字前一定要防 `inf`/`NaN`。

**（2）短/扁平箭头被当成误触整条丢掉**

`finishDrawing` 原来用**包围盒**判误触：`bounds.width < 3 || bounds.height < 3`。
而箭头（和细长矩形）的包围盒总有一边接近 0 —— 一条画得好好的水平箭头会被整条丢掉。

对照实测（水平拖 48 点）：

| 条件 | 结果 |
|------|------|
| 修复前 | ❌ **无批注 —— 整条被丢掉**（"箭头消失"） |
| 修复后 | ✅ 落成 `Line`，`Rect` 51×3 |

改法三处：

- 箭头用**线长**判误触（`hypot(Δ)`），不用包围盒
- 箭头的 `bounds` 外扩半个线宽、矩形/圆保证至少一个线宽的厚度 ——
  水平/垂直拖出来的 **零厚度 `Rect` 写进 PDF 后别的阅读器可能不画**
- 涂鸦的 `bounds` 同样外扩半个线宽（点集只是中心线的包围盒，描边还有一半在外面）

## 打包与分发（Direct Distribution）

一条命令出可直接发给用户的、**已公证**的安装包：

```bash
./tools/package.sh --version 1.4.0
```

产出：

```
dist/
├── PDF Free-1.4.0-arm64.dmg        Apple Silicon
├── PDF Free-1.4.0-x86_64.dmg       Intel
├── SHA256SUMS.txt
└── dSYM/                           崩溃符号化用
```

加 `--arch universal` 则只出一个双架构通用包。完整参数见 `./tools/package.sh --help`。

### 两个前置条件

**1. Developer ID Application 证书**

Direct Distribution 只认这一种证书。公司账号里那把 `Apple Distribution: KOOLMESH
TECHNOLOGY CO.,LTD` 是给 App Store 上传用的，**不能**走这条路（签出来的包公证会被拒）。

**不用去 developer.apple.com**，Xcode 里点两下就有：

```
Xcode → Settings…（⌘,）→ Accounts → 选中团队 → Manage Certificates… → + → Developer ID Application
```

`./tools/package.sh setup-identity` 会直接把你领到那个面板。

⚠️ 面板里已经列着同名证书，也要**在本机重建一张** —— 证书私钥只存在创建它的那台机器上，
别人建的证书拿过来也没法签名。

⚠️ 账号凭据（钥匙串里的 `Xcode-Token`）会过期。实测这台机器上 3 个 Apple ID
**全部失效**（`missing Xcode-Token`），要先在 Accounts 页重新登录一次。

**2. 公证凭据**（存一次就行）

```bash
./tools/package.sh setup-notary      # 要 Apple ID + Team ID + app 专用密码
```

app 专用密码在 appleid.apple.com → 登录与安全 → App 专用密码 生成，**不是登录密码**。

不确定齐没齐，跑 `./tools/package.sh doctor` 体检。

### 流程与理由

```
swift build（arm64 + x86_64 通用二进制）
  → 手工组装 .app（Info.plist 的 $(VAR) 占位符得自己替换）
  → 签名：Hardened Runtime + 时间戳
  → 公证 .app → staple  ← 让 app 自己带票据
  → 打 DMG → 签名 DMG
  → 公证 DMG → staple  ← 让 dmg 也带票据
```

**为什么 app 和 dmg 各公证一次**（默认 `--notary-mode app+dmg`，要跑 4 次公证）：
只公证 dmg 的话，用户把 app 拖进「应用程序」、再删掉 dmg，app 身上没有票据，
**离线双击可能被 Gatekeeper 拦**。两边都 staple 才是真正"离线也能验证"。
嫌慢可以 `--notary-mode dmg-only`，省一半时间，代价就是上面这条。

**为什么不用 xcodebuild**：这台机器上它跑不通（`swift-plugin-server produced
malformed response`，环境级问题）。所以走 `swift build` + 手工拼 .app。
拼出来的包结构和 Xcode 打的完全一致 —— 已实测：Info.plist 占位符、图标、
可执行文件、沙盒 entitlements 都对，签名后能正常启动。

**为什么证书那一步不能也自动拿**（试过了，两条路都堵）：

1. `xcodebuild -allowProvisioningUpdates` 确实能让 Xcode 自己去向 Apple 要证书，
   但它要先读 Xcode 账号在钥匙串里的凭据（`Xcode-Token`）。本机 3 个 Apple ID 的
   凭据**全部失效**（`Invalid credentials in keychain ..., missing Xcode-Token`），
   而首次登录要密码 + 双重认证 —— Apple 不允许无人值守跳过。
2. 就算凭据在，Developer ID 的正路是 `archive` → `exportArchive`（`method=developer-id`）。
   直接 `CODE_SIGN_STYLE=Automatic` + `CODE_SIGN_IDENTITY=Developer ID Application`
   会被 Xcode 拒掉：`conflicting provisioning settings ... automatically signed for
   development`。而 archive 必须先编译，本机命令行编译又是坏的。

⇒ **证书只在 Xcode GUI 里做一次**（Manage Certificates 那步不需要编译），
之后 `package.sh` 全自动。**只有"人"和"证书"这一步是手动的。**

### 两个踩过的坑（改脚本时注意）

- **bash 3.2 会把紧跟中文的变量名一起吞掉**：`"$VERSION，CFBundleVersion"`
  被解析成变量 `VERSION，CFBundleVersion`，报 `unbound variable`。
  macOS 自带的 bash 是 3.2（不是 UTF-8 aware）。**`$VAR` 后面接中文标点一律写
  `${VAR}`**。同一行 `local` 里也别引用同行的另一个 local（先声明后赋值，会撞 `set -u`）。
- **DMG 里的 app 包名必须正好是 `PDF Free.app`** —— 这个目录名就是用户装完看到的
  名字。区分架构只能靠**父目录**。曾经写成 `PDF Free-arm64.app`，用户那边名字就带后缀了。

### 改视图时必看：状态订阅

SwiftUI 的 `body` 只在**它自己观察的对象**变化时重新求值。所以有一条硬规则：

> **父视图不要直接读子模型的状态属性。**

错误写法（本项目已经踩过两次）：

```swift
struct ContentView: View {
    @StateObject private var viewModel = AppViewModel()   // 只观察 AppViewModel

    var body: some View {
        // ❌ isEditable 是 PDFViewModel 的 @Published。
        //    在这里读它，值变了 ContentView 不会重新求值。
        if let tab = viewModel.selectedTab, tab.viewModel.isEditable {
            AnnotationPalette(viewModel: tab.viewModel)
        }
    }
}
```

症状很有欺骗性：**「点了没反应」，切换标签或改一下窗口大小后突然正常了**。
编译器完全不报错，只能靠人发现。

正确写法 —— 父视图只决定「渲染哪个 tab」，把 tab 传下去，让子视图自己订阅：

```swift
private struct PaletteHost: View {
    let tab: DocumentTab
    @ObservedObject var pdfVM: PDFViewModel          // ✅ 自己订阅

    init(tab: DocumentTab) {
        self.tab = tab
        self.pdfVM = tab.viewModel
    }

    var body: some View {
        if pdfVM.isEditable { AnnotationPalette(viewModel: pdfVM) }
    }
}
```

改完视图跑一下检查脚本（它会先自检，确认检查器本身没失灵）：

```bash
python3 tools/check_view_observation.py --selftest   # 自检：能否抓到已知坏样本
python3 tools/check_view_observation.py              # 扫描 Sources/PDFReaderApp/Views
```

历史上因此出过的问题（都是同一个根因）：

- 新增批注后左侧列表不刷新，要切换一次面板才出现（`AnnotationSidebar` 用了 `let viewModel`）
- 点「编辑」工具条不出现、输入搜索词右侧结果栏不出现（`ContentView` 读了 `tab.viewModel` 的属性）

### 顶栏与布局

```
[只读/编辑] [打开] [左右栏开关] [←→] [页码] [书签] … [缩放][布局][朗读][滚动][OCR][更多]   [🔍 搜索]
──────────────────────────────────────────────────────────────────────
[工具…] | [颜色][不透明度][线宽/字体]                              ← 仅编辑模式（样式段可横向滚动）
──────────────────────────────────────────────────────────────────────
[文件A | 文件B | 文件C]                                          ← 常驻，等宽平分
──────────────────────────────────────────────────────────────────────
[左侧栏：缩略图/目录/批注/书签] | [页面] | [右侧栏：属性 / 搜索结果]
```

- 多文件走**系统窗口标签页**（一个文件一个窗口）；窗口上方那一条就是 macOS 的标签栏，
  打开一个文件就已经显示（v1.3.45）。
- 搜索在**右上角常驻**，输入即搜；结果在右侧栏，点一条会把命中处滚到**页面正中**。
- **左右侧边栏都可以手动关闭**：顶栏「打开」按钮右边有两个开关（图标会随状态变），
  左右栏各自的角上也有 ×。关掉之后用顶栏的开关再打开。
- **栏宽会被记住**：宽度直接绑到 `UserDefaults`（`pdfreader.leftSidebarWidth` /
  `rightSidebarWidth`），拖动分隔条即时写入，**关掉侧边栏再打开也还是那个宽度**。
  这里**没有用 `HSplitView`** —— 它在动态增删子视图时会重新分配宽度、不尊重 `idealWidth`，
  表现就是"关掉再显示，宽度又变回默认值"。改用自绘的分隔条（`ResizeHandle`）后，
  宽度完全由我们控制，也能保证"删标注时右侧栏不消失"。
- **右侧栏不会因为内容变空而消失**：删掉一条标注后它留成空白（带一句「未选中标注」的说明），
  只有你点关闭才收起。否则每删一条标注就抽掉一整栏，页面宽度会跟着横跳一下。
  这也是它和左侧栏的区别 —— 左侧栏是常驻的，右侧栏是"用过之后留在那儿"。
- **切回只读时会自动收起右侧栏**（属性栏只读模式下没意义了）。
  例外：如果正在搜索就不收 —— 那时右侧栏装的是搜索结果。

### 侧边栏的开/关**只有顶栏那一个入口**（v1.3.46）

左侧栏面板头、右侧栏"属性"空状态、标注属性栏头部原来各挂了一个 `×` 关闭按钮，
现在都去掉了 —— 顶栏已经有开/关左右侧栏的按钮（`sidebar.left` / `sidebar.right`），
栏内再放一个既是重复入口，也让左侧栏那个四分段切换器白占窄一截宽度。
**"取消选中标注后右栏留白"这条行为没变**（有意如此，栏位一收一放会让页面宽度抖一下）。

### ⚠️ 侧边栏里的内容**不许撑破栏宽**（v1.3.47）

症状：右栏拖到一定窄度之后，那条**分隔条拖不动**了；把标注取消选中（右栏变空状态）
又能拖。

根因：`.frame(width:)` **不裁剪**。属性栏里那排颜色圆点
（8 个色点 + 「透明」+ 取色器 ≈ **278pt**）比栏的最小宽 200 还宽，于是内容左右各溢出
约 39pt —— 而 **SwiftUI 里溢出的部分照样吃点击**，正好盖住那条 6pt 宽的分隔条。
（同一个坑在 `FontControls` 上出现过一次，那次是把它改成分两行。）

三层修法：

1. **治本**：`ColorSwatchRow` 在窄容器里**自动换行**（`wraps: true` →
   `LazyVGrid(.adaptive)`，列宽由容器决定，所以永远不超）；
2. **保险**：侧边栏加 `.clipped()` —— 它**连命中区一起裁**，以后再有控件撑破，
   最坏也只是显示不全，不会再把分隔条废掉；
3. **保险**：分隔条 `.zIndex(1)`，事件优先权归它。

还加了一条**运行时自检**：`RightPanelView` 用 `PreferenceKey` 把内容的**自然宽度**
报给 `DocumentLayout`，一旦 `内容宽度 > 栏宽` 就记一条
`⚠️ 属性栏内容比栏宽还宽`（附对照实验：关掉换行时它确实会报 `内容 260 > 栏宽 200`）。

### ⚠️ 收放侧边栏**不会**改变页面缩放（v1.3.10）

早先只要动一下侧边栏，页面就会"自己缩一下"：PDFView 宽度变了，
`autoScales` 就按"适合宽度"重新适配（实测关一次左栏，缩放 1.25 → 1.61）。

**关键在"什么时候记下缩放"。** 第一版想在 `layout()` 里跟"上一帧"比 —— **没用**：
实测 PDFKit **在宽度变化的过程中**就已经把 `scaleFactor` 重算好了，
等 `layout()` 被调到，读到的已经是新值，那会儿再"还原"等于还原成新值。

现在的做法：

```swift
// PDFViewModel：在"会改变 PDFView 宽度的操作"之前调用
func beginPreservingZoom() {
    (pdfView as? EditablePDFView)?.zoomToPreserve = pdfView.scaleFactor
}
// EditablePDFView：布局时把它还回去
override func layout() {
    ...
    super.layout()
    guard widthChanged, let target = zoomToPreserve, document != nil else { return }
    if abs(scaleFactor - target) > 0.0001 { scaleFactor = target }
}
```

调用点：顶栏的左右栏开关、两条分隔条的**拖动起始**（`onDragStart`，不能每帧调，
否则记下的是已被改过的值）、`revealRightPanel()`（属性栏弹出时）、切回只读收起栏位时。

配套：用户自己缩放后要 `syncPreservedZoom()` 更新基准（否则下次切栏位会把用户的缩放还回旧值），
换文档或点「适合宽度」时清掉（`resetPreservedZoom()`）。

> 顺带一个实测结论：**给 `scaleFactor` 赋值会顺带把 `autoScales` 关掉**。
> 所以切过一次侧边栏之后，拖窗口也不会再自动"适合宽度"了 —— 想回到自动适配点一下
> 「适合宽度」按钮。这与"别自己缩放"的诉求是一致的。

> 抓手模式下光标变手型（拖动时握拳），松开空格即恢复。空格只在 PDFView 所在窗口生效，
> 不会影响搜索框、便签输入框里的空格输入；按住空格时切到别的 app 也会自动复位。

> 缩放锚点补偿的两个关键点（都是实测确认的，改动前请先读 `ScrollZoomMonitor.swift` 里的注释）：
> 1. `clipView.bounds` 处于 documentView 坐标系，**1 个单位 = `scaleFactor` 个屏幕点**，
>    补偿量必须先除以 `scaleFactor`。
> 2. 边界交给 `NSClipView.constrainBoundsRect` 判断，**不要手写 clamp** ——
>    它在内容小于视口时会返回居中值，手写 `min(max(origin, 0), upper)` 会破坏居中。
>
> 横向页宽小于视口时，页面保持居中、不做锚点补偿，这是正确行为（没有可滚动的余地）。

## 批注拖动

**可拖动**：便签、文本注释、手写签名 —— 这三类的共同点是"自带矩形框、框内就是全部内容"。
**不可拖动**：高亮 / 下划线 / 删除线，它们是锚定在正文文字上的，搬走矩形框会让标注和文字脱节。

实现见 `Views/EditablePDFView.swift`，几个不能想当然的地方：

- **改 `bounds` 就够了，不用重算笔迹。** PDFKit 的 ink 路径坐标是**相对批注 bounds 原点**的
  （`PDFAnnotationInk.h` 明确写了），所以整体平移只改 `bounds` 即可。
- **拖动必须保持 `size` 不变。** 实测：把 `bounds` 尺寸放大一倍，笔迹**不会**跟着放大 ——
  路径不随 bounds 缩放。尺寸一变就是"框大了但字没大"的错位。
- **必须通知 PDFView 重绘**（`annotationsChanged(on:)`），否则屏幕上还是旧位置。
- **3 点阈值区分拖动与单击**：没超过阈值就当作普通单击，把原事件交回 PDFView，
  这样"点便签图标弹出内容""点链接跳转"等原生行为不受影响。
- **⚠️ 单击放行前必须先往事件队列补一个抬起事件**（`NSApp.postEvent(event, atStart: true)`）。
  PDFView 的 `mouseUp` 会把抬起事件**取走再放回**，而真实的抬起事件此刻已经被我们消费掉了 ——
  不补，界面会**永久卡死**直到用户再点一次（实测：不补 → 挂起；补了 → 立即返回）。
  补进去的事件按对象身份回收（`reclaimPostedEvent`），不会误吞用户自己的事件。
- **位置钳在所在页内**（`cropBox`）：批注是挂在某一页上的，拖出页面既看不见也找不回来。
- **为什么不用 `isInMarkupMode`**：PDFKit 自带的这个开关在 macOS 26 已废弃，
  且会带来自己的批注编辑手势，与「空格抓手」「⌥+滚轮缩放」两个全局监听抢事件；
  它也不区分批注类型，高亮会被一起拖走。

拖动结束后批注列表会刷新（修改日期变了）。列表的实时刷新依赖
`AnnotationSidebar` 上的 `@ObservedObject` —— **别把它改回普通 `let`**，
否则新增批注后列表要切换一次面板才更新（SwiftUI 会对子视图做记忆化比较，
类引用没变就跳过 body 求值）。

## 文本注释的框自适应

新建文本注释时，框的尺寸按内容算出来（`Utils/FreeTextLayout.swift`），
不再写死高度 —— 一行文字就是一个矮框，内容多就自动加高，不会被裁。

### PDFKit 对 FreeText 的排版规则（实测）

| 行为 | 结论 |
|------|------|
| 长文本 | **会自动换行**，中英文都会（英文按词、中文按字符） |
| `\n` | **认**，空行也占一行 |
| 框高不够 | **直接裁掉** —— 不会缩字号、也不会溢出到框外 |
| 内边距 | 左右各 3 点；框顶到首行墨迹约 6 点 |

**关键是**：PDFKit 的换行结果与
`NSAttributedString.boundingRect(options: [.usesLineFragmentOrigin, .usesFontLeading])`
**完全一致** —— 这是能算准尺寸的前提。

### 换行策略

**`\n` 决定换行；只有最长的一行超过 `maxWidth` 才自动折行。** 我们不去替用户折。

`maxWidth` 存在批注自己的键里（`/PRMaxWidth`），新建时写一次
（取「可见区域宽的 90%，且不超过 320」）。**必须存** —— 事后重排若拿不到它，
就只能拿"现有宽度"凑合，那会导致**改小一次字号就再也长不回去**：

| 内容 | 15号 | 32号 | 回 15号 |
|------|------|------|---------|
| 短备注 | 53×21 | 100×41 | **53×21 ✅** |
| 含 `\n` | 142×39 | 282×79 | **142×39 ✅** |
| 很长（超 320） | 320×57 | 320×231 | **320×57 ✅** |

### 尺寸公式

```
文字高度 = boundingRect(可用宽度).height      // 上取整
框高     = 文字高度 + 3
框宽     = min(maxWidth, max(文字自然宽 + 6 + 2, 44))
```

`+ 3` 是**常数**（`FreeTextLayout.textPadding`）—— 这一点返工过一次：

> 早先是 `max(6, ceil(字号 × 0.5))`，只在 8~18 号标定过，往大字号是**线性外推**。
> 实测底部留白随字号一路涨，72 号时框里白白多出 **39 点**（"背景比文字大一圈"）：
>
> | 字号 | 8 | 12 | 15 | 18 | 24 | 36 | 48 | 72 |
> |------|---|---|----|----|----|----|----|----|
> | 旧留白 | 7 | 7 | 9 | 10 | 13 | 20 | 26 | **39** |
> | 新留白 | 4 | 4 | 4 | 4 | 4 | 5 | 5 | **6** |
>
> 根因是重复计算：**CoreText 自己算的高度已经把行高、上下伸部都算进去了**
> （`boundingRect(options: .usesFontLeading)` 与
> `CTFramesetterSuggestFrameSizeWithConstraints` 实测完全一致），
> 再叠一个字号相关的余量纯属重复。改成常数后 8~72 号**全部不裁切**。
>
> （验证手法：把框设成算出来的高度，渲染后量墨迹包围盒，与"给一个巨大框"的参考墨迹逐项对比，
> 高度/宽度差 < 1.5 点才算"完整"。）

### ⚠️ 存盘后 `annotation.font` 会失真

PDFKit 保存后再打开，`annotation.font` **恒为 Helvetica 12**（15 号、18 号都被报成 12），
`/DA` 也读不到了 —— 但**渲染尺寸其实是保留的**（重载后墨迹高度与原来一致）。

所以 `FreeTextLayout.effectiveFontSize(of:)` 按这个顺序取真实字号：

1. `/DA`（DefaultAppearance）里的 `N Tf` —— 新建或本次会话改过的批注都能读到
2. **按现有框高反推** —— 我们建的批注高度就是按公式算的，取"算出的高度 ≥ 现有高度"里最小的字号。
   方向刻意偏保守：宁可把字号猜大（框偏大），也不猜小（框偏小会裁）
3. `annotation.font`
4. 默认字号

实测：造 12/15/18 三档批注各存盘重载，`annotation.font` 全部报 12，而按上面顺序**全部还原正确**，
用还原出的字号执行"框适应内容"后依然不裁切。

### 字号与清晰度

**默认字号 15**（不是 PDF 注释惯用的 12），弹窗里可选 小 12 / 中 15 / 大 18，记住上次选择。

为什么默认不用 12：把同一段文字在**真实栅格化倍率**下量"中间调像素占比"（越大观感越糊）——

| 栅格化倍率 | 12 号 | 15 号 | 18 号 |
|-----------|-------|-------|-------|
| 1.4×（≈「适合宽度」显示） | 0.266 | 0.231 | 0.193 |

字越小，笔画越容易被栅格化抹成灰边。**这是"文本注释看起来模糊"的主因**——
批注文字本身与同字号的页面正文渲染完全一致（着墨像素 6128 vs 6128）。

### 两个容易踩的点

- **别为了"跟存盘后的字体对齐"改用 Helvetica。** PDFKit 保存后再打开，
  `annotation.font` 会变成 Helvetica 12（原来的系统字体没被保留）。看起来换成 Helvetica
  更"一致"，但实测**中文全部被裁**：PDFKit 渲染中文时会回退到真正的 CJK 字体，
  而这个回退结果与 AppKit 用 Helvetica 量出来的换行结果**不一致**，差一整行。
  系统字体两边都会回退到同一个 CJK 字体，所以才是对的。
  存盘重载后墨迹最多长 1 点，`bottomMargin` 的余量足以吸收。
- **框宽要留 2 点余量。** 若可用宽度正好等于文本宽度，末尾字符可能被挤到下一行，
  高度就会少算一行（15 点）→ 又被裁。

### 已有的被裁批注

旧的实现写死 48 点高，之前创建的文本注释可能仍然被裁。两个补救入口：

- **单条**：批注列表里右键 → 「框适应内容大小」（会按内容重新贴合，含收掉多余空白）
- **批量**：批注面板底部「修复被裁切的文本注释」——
  **只加高、不放矮、也不改宽度**。批量操作可能碰到别的应用创建的批注，保守一点只修确实有问题的。

批量操作不会自动执行，必须手动点 —— 改别人的批注不该悄悄发生。

## 标注工具

顶栏最左是 **只读 / 编辑** 开关。**打开文件默认只读** —— 只能看，改不了任何东西；
点「编辑」后，标注工具条出现，标注才可以新增、拖动、删除、写回文件。

| 工具 | 交互 |
|------|------|
| 选择 | 点选标注，按住拖动改位置；按 Delete 删除 |
| 高亮 / 下划线 / 删除线 | 选中文字后松开即套用（也可以先选好文字再点工具）。**跨行选择按行逐段标注** |
| 文本注释 | 在页面上**点一下**决定位置，再输入内容 |
| 画笔涂鸦 | 按住拖动自由绘制 |
| **直线** | 按住拖动，两端都不带箭头 |
| 矩形 / 圆 / 箭头 | 按住拖出形状（方向任意，反向拖也对） |
| 便签 | 点一下决定位置（图标居中在点上） |
| 手写签名 | 点一下决定位置（签名居中在点上），再手写 |

每个按钮的悬停提示会写清"怎么用"（比如"矩形：在页面上按住拖动"），不用逐个试。

**全部是矢量。** 所有标注都落成标准 PDF 批注（`Square` / `Circle` / `Line`+箭头 / `Ink` /
`FreeText` / `Text` / `Highlight` / `Underline` / `StrikeOut`）。

- 形状类：实测 1× 与 4× 栅格化下墨迹尺寸差 **0.00 点**。
- **文本注释同样是矢量的**，两条独立证据：
  1. 写盘后的 PDF 里**没有任何图像对象**（搜索 `/Subtype/Image`，纯正文/矩形/涂鸦/文本注释四种文档全部为 0 个）；
  2. 让 `PDFView` 渲染并导出后，**批注文字仍能被 `findString` 搜到** ——
     被栅格化成图像的文字是搜不到的（同一测试里页面原有正文反而搜不到，
     因为 `dataWithPDF` 把页面内容栅格化了，而批注是以文本对象重绘的）。

  所以觉得文字"糊"的话，那是**字号偏小 + 屏幕栅格化**的观感问题，不是矢量与否 ——
  默认字号已经因此从 12 提到 15；字号可在 **8~72** 之间连续调（工具条/属性栏的滑条，
  或新建弹窗里的 ± 按钮）。

### 外观可调项（v1.3.9 扩过一轮）

| 项 | 说明 |
|----|------|
| 颜色 | 8 色调色板 + 自定义取色器 + **「透明」**（完全不上色，见下） |
| 不透明度 | 0~100% 连续滑条。高亮和文本注释背景**另有基础半透明系数**（见下） |
| 线宽 | **0.5~24 连续**（滑条），也能用 ± 以 0.5 为步长手动加减 |
| 文字颜色 | 文本注释**单独一项**，和背景色分开调（取色器带透明度） |
| 字体 | 18 个族（系统默认 / 苹方 / 宋体 / 黑体 / 楷体 / 华文宋体 / 华文楷体 / 冬青黑体 + Helvetica / Times 等），字号 8~72，**加粗 / 斜体** |

> **高亮和文本注释背景为什么拉满也只有一半 / 22%**：
> 它们是"涂在正文上的淡色"，实心会糊住字。所以滑条是在一个基础系数上乘的 ——
> 高亮 `opacity × 0.5`、文本注释背景 `opacity × 0.22`，其余种类就是 `opacity` 本身。
> 滑条拉到 100% 时高亮是 50% 浓度，这正是想要的观感。

> **斜体对部分字体无效**：中文字体基本都没有斜体面（实测苹方/宋体/黑体/楷体/冬青全都没有），
> `STSong` / `STKaiti` 连粗体都没有。这两条合成路线都试过、**都不行**：
> `NSFontDescriptor.withMatrix(斜切矩阵)` 会让中文字**一个像素都画不出来**；
> CoreText 的 `.obliqueness` 属性在 `CTLineDraw` 路径上完全没效果。
> 所以界面在选中这类字体时**把「加粗 / 斜体」按钮置灰**并说明原因，而不是给一个按了没反应的按钮。

### 「透明」的语义与适用范围（v1.3.10）

**透明 = 不上色。** 实现在自绘侧显式拦截，因为交给 CGContext 会出问题：

> ⚠️ **`alpha = 0` 的颜色会被 PDFKit 变成"空 NSColor"**（`usingColorSpace(.sRGB)` 返回 nil、
> `/C` 变 nil）—— 不管赋的是 `NSColor.clear`（那是**单色 Monochrome** 色彩空间）
> 还是正经 sRGB。把这个空色交给 `CGContext.setStrokeColor`，它**不报错，
> 而是沿用上一次的颜色兜底**，默认就是**黑色**。用户看到的就是"选了透明，形状画出来是黑的"。
>
> 所以 `AnnotationRenderer` 里显式拦掉 `alpha <= 0.004` 的批注（`transparentThreshold`），
> 预览图层同理。

只对**带背景/填充**的种类有意义 —— 只有**高亮**和**文本注释背景**支持：

| 种类 | 透明是什么意思 |
|------|---------------|
| 高亮 | 不涂色（等于没有高亮） |
| 文本注释 | **只去背景，文字照画**（字色在上面的「文字颜色」单独调） |
| 矩形/圆/直线/箭头/涂鸦/下划线/删除线/便签 | **不提供** —— 描边类没有颜色就是看不见，那不是用户要的结果 |

调色板/属性栏在不适用的种类下**不显示**这个选项；`applyStyle(to:)` 里还有一道兜底，
遇到"种类不支持却带着透明状态"会自动纠正回有色（比如先给高亮选了透明，再切去画矩形）。

### 跨行文字批注：一条批注 = 一组 quad（v1.3.9 修的）

早先给高亮/下划线/删除线只设 `bounds = selection.bounds(for: page)`，
**跨行选择时那是一个包住所有行的大矩形** —— 行间空隙、每行没选到的横向范围全被涂上，
屏幕上就是一块实心色块，和实际选中的文字对不上。

现在按 `selection.selectionsByLine()` 逐行切成 quad 点写进 `quadrilateralPoints`
（一条批注、一组 quad，和 Preview 的做法一致）。两个坑：

1. **坐标是批注空间**（相对 `bounds` 原点），不是页坐标。塞页坐标进去整组 quad 会平移出选区
   （实测"画到选区外 17 行"）。
2. **每个 quad 的四点顺序是「左上、右上、左下、右下」**（PDF 32000-1 Table 8.47，
   PDFKit 自己产出的批注也是这个顺序）。顺序写错会画成"蝴蝶结"：
   同一行里上下两段、中间空一条。

自绘那边也一并支持了多 quad（`AnnotationRenderer.quadBoxes`），
所以跨行高亮**仍然是清晰的矢量**，不会因为"段数多"就退回 PDFKit 的 1x 栅格化。

### 外观的持久化：PDFKit 存不住的那几项（v1.3.9）

实测把 `PDFDocument.dataRepresentation()` 写盘再读回来，逐项对比：

| 属性 | 写进去 | 读回来 | 结论 |
|------|--------|--------|------|
| `annotation.color` 的 **alpha** | 0.5 / 0.3 / 0.4 | **1.0** | ❌ 丢了（alpha = 0 例外，会变成"无颜色"） |
| `annotation.fontColor` | systemBlue | 灰度黑 | ❌ 丢了 |
| `annotation.font` | Helvetica-Bold 20 / PingFangSC-Semibold 18 | **恒为 Helvetica 12** | ❌ 丢了 |
| `/DA`（DefaultAppearance） | — | **nil** | ❌ 指望不上 |
| **自定义键**（`/PRFontFamily` 等） | "Helvetica" | "Helvetica" | ✅ **能往返** |

不处理的话，"存盘再打开"会变成：高亮变实心、文字变黑、字体回到 Helvetica 12。
所以透明度 / 文字颜色 / 字体族 / 字号 / 粗斜体都存在自己的键里
（`AnnotationAppearance`，`/PR…` 前缀，未知键 PDF 会忽略，不影响互操作），
**文档加载时再 `restore` 回原生属性**（挂在 `applyDisplayPolicyToDocument` 里）。

> 这也是**默认字号不用 `/DA` 反推**的原因：`/DA` 实测读不到。
> 现在优先读 `/PRFontSize`，再退化到"按框高反推"（别的应用建的批注没有我们的键）。

### 批注的渲染方式：**存成 PDF 批注，但由我们自己画**

> 这是 v1.3.6 的核心改动。批注**依然落成标准 PDFAnnotation**
> （写盘、打印、与其他阅读器互操作都靠它），但**屏幕显示改由 `AnnotationRenderer` 自绘**。

**为什么要自绘 —— 两条实测结论，正好对应你反馈的两个现象：**

| 现象 | 实测根因 |
|---|---|
| 「松手之后才会出现」「要切页才显示」 | PDFKit 的**批注层在鼠标拖拽期间不刷新**。实测：按住拖动连续改 `bounds`，屏幕纹丝不动（红色像素恒为 32），松手重建 document 才出现（52334） |
| 「看起来并不是光滑的矢量」 | PDFKit 的页面层 `contentsScale` 是 **1.0**，而屏幕 `backingScaleFactor` 是 **2.0** —— 批注是 1x 栅格化后放大显示的，边缘必然发虚。实测 PDFKit 画的批注与页面正文**同样模糊**，而 `drawPagePost` 里用 CGContext 画的同样形状**明显更锐利** |

自绘走的是 PDFView 自己的层（`drawPagePost`），**原生屏幕分辨率 + 拖拽期间实时重绘**：

```
实测（真实文件 + 真实事件循环）：
  基线    红色=34
  按下    红色=34
  拖动1   红色=18656   ← 拖动中就显示了
  拖动2   红色=39799
  拖动3   红色=61076
  松手    红色=61076   ← 无缝衔接（草稿转正式批注，数值不变）
```

**实现要点：**

- **草稿不进 PDF，而且拖动期间连草稿批注都不改。** 按下时只建一个内存里的 `PDFAnnotation`
  作为草稿，**松手才 `addAnnotation`**。
  > v1.3.8 起更进了一步：涂鸦拖动期间**一个字都不写进那个草稿批注**（只 `append` 点，
  > 几何由 `AnnotationRenderer.inkPaths(points:)` 现算），落成笔迹放到松手那一次做。
  > 原因是每来一个点重建整条笔迹的成本是 O(点数)，900 点时事件滞后就冲到 80 ms（详见 v1.3.8）。
  > 形状类只改 `bounds` 和两个端点，本来就是 O(1)，不受影响。
- **拖动期间不请求 `needsDisplay`。** 预览完全由独立 `CAShapeLayer` 承担；
  `drawPagePost` 里"画草稿"那段已降级为真·兜底（只在预览图层没挂上时才生效）。
  实测 `drawPagePost` 调用次数从 448 降到 46。
- **已有的批注也要接管。** 文档加载后调 `applyDisplayPolicyToDocument()`，
  把能正确渲染的批注设成 `shouldDisplay = false`（PDFKit 不再画），由 `drawPagePost` 画 ——
  这样**别的应用创建的批注也能以清晰的方式显示**。
- **`isSelfRendered` 只接管"我们能完整正确渲染的"。** 多段 quad 的高亮/下划线、
  没有笔迹的 ink、退化的 line 一律交回 PDFKit —— 宁可那一个保持 PDFKit 的观感，
  也不要画错或画丢。
- **箭头的三角按 PDFKit 实测标定**（头长 4.6×线宽、半宽 2.25×线宽、尖端外扩 1×线宽）。
  细节与标定表见上面 v1.3.8。旧版小一圈，看着像"三角没到位"。

### ⚠️ `shouldDisplay = false` 有四个连带影响，都必须处理

实测确认：**这个标志会被持久化到文件里**（设 false 写盘后重开仍是 false）。
所以只要用了它，下面四条一个都不能漏：

| 影响 | 处理 |
|---|---|
| **写回文件** —— 别的阅读器打开会**看不到批注** | `saveAnnotationsToDisk` 写盘前恢复 `shouldDisplay = true`，`defer` 里再设回 false |
| **打印** —— `page.copy()` **会保留 false**，打印出来**一个批注都没有**（`includeAnnotations = true` 也一样） | `PDFPrintService.duplicatePages` 对副本调 `forceAnnotationsVisible`；并且只要文档里存在隐藏批注，`makePrintableDocument` 就**必须走重建路径**（"全部页 + 不拼版"那条直通原文档的捷径要禁用） |
| **PDFKit 的批注交互全部失效** —— `page.annotation(at:)` 对 `shouldDisplay = false` 的批注返回 **nil** | 我们自己的命中测试是**几何判断**（`annotation.bounds.contains`），不依赖它 ✅；但"点便签弹内容"原本由 PDFKit 提供，**要在只读分支里自己补**（`presentNoteContents`） |
| **缩略图** | **不受影响**（实测 `page.thumbnail` 根本不渲染批注，改不改都一样）|

### 另外三个必须记住的实现细节

- **刷新只需两件事**，统一走 `notifyAnnotationsChanged(on:)`：`annotationsChanged(on:)`
  失效该页渲染缓存（主要用于擦掉 PDFKit 之前画过的那一份）+ **递归标脏整棵视图树**。
  页面内容画在内部的 `PDFPageView` 上，而 **`needsDisplay` 不会传导给子视图**，
  只标 PDFView 那一层的话页面内容纹丝不动。

  > 历史上这里试过一长串"重手段"（`layoutDocumentView()`、`go(to: 当前页)`、
  > 甚至重建整个 `document`），前提都是**指望 PDFKit 重画批注**。
  > 改成自绘后这些全都不需要了，已删除。其中 `layoutDocumentView()`
  > 实测**完全不触发页面绘制**（`drawPagePost` 计数 +0），当时是白加的。

- **箭头（Line 批注）的 `startPoint`/`endPoint` 是「批注空间」**（相对 `bounds` 原点），
  不是页坐标。用页坐标画出来会被整体平移 `bounds.origin` 那么多 —— 表现是"拖了半天，线画在别处"。
  换算见 `AnnotationGeometry.linePointsInAnnotationSpace`。
- **拖动箭头时 startPoint/endPoint 千万不要跟着平移** —— 它们是**相对 `bounds` 原点**的坐标
  （"线在框里的位置"）。平移 `bounds` 时 PDFKit 会保持这个相对关系，线自己会跟着框走。
  **多平移一次就会平移两次** —— 表现是拖动时箭头飘出虚线框、被裁成只剩一部分。
  这一条之前写反过，实测确认：只改 `bounds`，`start`/`end` 原样不动。
- **矩形/圆的描边画在 `bounds` 内侧**，拖出来的框就是画出来的框（实测墨迹与 bounds 完全一致）。

### 箭头：线身与箭头是**同一条轮廓**（v1.3.14）

**问题**：自绘时线身走描边、箭头走填充，是两个独立图元；线条端头又是**圆头**
（`lineCap = .round`），而箭头底边是**平的** —— 圆头与平底边**只相切于一个点**。
两个图元各自抗锯齿、各自铺色，接缝那一列的 alpha 只有 0.75（0.5 + 0.5×0.5），
放大 4 倍就是一条贯穿的浅色竖缝，看着像"一根管子顶着一个帽子"。
用户的原话是「没有完全贴合，看着很奇怪」。

**改法**：把线身与实心端点合成**一条闭合轮廓、一次填充**（`solidOutline`）。
重点不是"把两段几何对齐"，而是**根本只有一段几何** —— 接缝无从而生。

轮廓（逆时针）走一圈：`尖端 → 钩尖 → 内凹 → 线身 → 内凹 → 钩尖`。
两个"内凹点"之间那段直线就是线身的上边缘，所以线身天然长在箭头上。

**箭头形状也从平底三角改成了倒钩**（`barbNotch = 0.75`）：钩尖向后张开成锐角，
再从钩尖斜切回线身边缘，指向性更强，线身正好接在凹口里。

**量化**（线宽 6、放大 4 倍，沿中轴扫最亮像素；纯红 g=13，背景 g=247）：

| 版本 | 端点形状 | 线身与箭头 | 轴线最亮 g |
|------|---------|-----------|-----------|
| v1.3.12 及以前 | 平底三角 | 两个图元，有接缝 | **92** ← 那条缝 |
| v1.3.14 | 倒钩 | 同一条轮廓 | **13** ← 干净 |

半透明（α=0.55）时中轴实测 g=119，与理论值 118 一致 —— **重叠叠色也一并消失**。

**端点样式的分工**（见 `linePaths`）：

| 端点 | 处理 | 原因 |
|------|------|------|
| 闭合箭头 / 无（圆头） | 并入同一条轮廓 | 接缝最刺眼的地方 |
| 开放箭头（V） | V 描边，**线身仍走轮廓** | V 是空的、不能填充；线身若也描边会被画两遍 |
| 圆点 / 方块 | 追加到同一份 `fill` | 都比线宽大，会把线身端头整个包住，同样不叠色 |

> ⚠️ **两个反直觉的坑**（都是探针测出来的，别凭直觉改）：
>
> 1. **多子路径的绕向必须一致。** nonzero 填充下，两条**反向**的子路径重叠区
>    winding = 1 − 1 = 0，会被**挖空**。手写矩形是顺时针、`addEllipse`/`addRect`
>    是逆时针 —— 混在一起，圆点端帽就被啃掉一块白弧。
> 2. **垂直方向 `perp` 不能从该端的 `dir` 现推。** start 端的 `dir` 是反向的，
>    现推的垂直方向会跟着翻 180°，那一端的"上钩尖"跑到下方去、轮廓上下自交，
>    **线身整段画不出来**（探针量到线身高度 `300:0`）。两端必须共用整条线的 `(-uy, ux)`。

> 注：**别的阅读器和打印仍会看到平底三角**（半透明时还可能看到那条叠色带）——
> 文件里存的是 `/Line` + `/LE`，阅读器按 PDF 规范自己画；打印也走 PDFKit 渲染而非我们的自绘。
> 这属于"跨阅读器的固有差异"。

### ⚠️ 自绘 ink 时的 CTM 陷阱（踩过一次）

`CGContext` 的**当前路径在 `addPath` 那一刻就被 CTM 固定了**，之后再 `translateBy` 完全无效：

```swift
// ❌ 图形被画在 (0,0)，而不是目标位置
context.addPath(path.cgPath)
context.translateBy(x: bounds.minX, y: bounds.minY)
context.strokePath()

// ✅ 先把路径变换好再加
var t = CGAffineTransform(translationX: bounds.minX, y: bounds.minY)
context.addPath(path.cgPath.copy(using: &t)!)
context.strokePath()
```

实测三种写法的落点：`addPath → translateBy` **画在 (0,0)**；
`translateBy → addPath` 正确；`cgPath.copy(using:)` 正确。

> 这个 bug 差点漏过去：探针当时报"637 像素 ✅"—— 我数了像素却**没验证位置**。
> 教训：**渲染类断言必须同时验"画出来了"和"画在哪"**。


### 拖拽绘制为什么要用独立图层（v1.3.7）

> 起因是"拖矩形时图形跟不上鼠标，像掉帧"。

**先把延迟量出来**（真实文件 + 真实事件循环，测「mouseDragged 到达 → 屏幕重绘」）：

| 指标 | 实测值 |
|------|--------|
| 事件处理滞后（事件在队列里等多久） | 8.4 ms（**稳定，没有积压**）|
| **事件 → 重绘** | **平均 38.6 ms，中位 42.6，P90 78.7，最慢 91.3** |
| `super.drawPagePost` | 0.0 ms |
| **我们自己的批注绘制** | **0.3 ms** ← 我们的代码几乎不耗时 |

60 fps 是 16.7 ms/帧。**38 ms ≈ 2.3 帧**，快速拖动时累积成肉眼可见的"图形落后于鼠标"。

**开销不在我们的绘制代码里，而在 `pdfView.needsDisplay = true` 触发的整页重绘** ——
PDFKit 要重新合成页面内容。试过**只标脏草稿区域**（`setNeedsDisplay(rect)`），
**没有任何改善**（43.7 ms），说明 PDFKit 的重绘开销与标脏范围无关，它总是重绘整页。

**解法：拖动中的草稿画在独立的 `CAShapeLayer` 上，完全不触发 PDFView 重绘。**

```swift
// 两个子图层：描边 + 填充（放 PDFView.layer 上，压在页面之上）
draftStrokeLayer / draftFillLayer

// 坐标：页坐标 → 视图坐标（三点采样推导，能正确处理缩放/翻转/旋转）
let origin = convert(.zero, from: page)
let unitX = convert(CGPoint(x: 1, y: 0), from: page)
let unitY = convert(CGPoint(x: 0, y: 1), from: page)
CGAffineTransform(a: unitX.x - origin.x, b: unitX.y - origin.y,
                  c: unitY.x - origin.x, d: unitY.y - origin.y,
                  tx: origin.x, ty: origin.y)

// ⚠️ 必须关隐式动画
CATransaction.begin()
CATransaction.setDisableActions(true)
draftStrokeLayer.path = movedPath
CATransaction.commit()
```

`CAShapeLayer.path` 的更新由 Core Animation 在渲染服务器上处理，主线程只做一次赋值。
实测**拖动后 20 ms 截屏，图层方案已经画出**（432 像素），而视图重绘方案**连 60 ms 都还没出现**。

**三个容易漏的点：**

- **`CATransaction.setDisableActions(true)` 不能省。** 否则每次改 path 都会走 0.25 秒的
  隐式补间动画 —— 看起来正是"图形慢慢追鼠标"，把问题变得更糟。
- **线宽要乘 `scaleFactor`。** `paths(for:)` 给的是页坐标的路径和页坐标的线宽，
  转到视图坐标后路径被缩放了，线宽不跟着乘就会粗细不符。
- **几何要共用。** 形状构建抽成 `AnnotationRenderer.paths(for:)`，
  让「画进 CGContext」和「预览图层」用**同一套几何**，否则拖动预览和松手后的结果会跳变。

**松手时**：不立即隐藏图层，而是让它留到下一次 `drawPagePost`（那时真批注已经画好），
再从 `drawPagePost` 里收起 —— 这样"草稿 → 正式批注"之间没有中间态，不会闪出空白。

> 用到的探针手法：`CGWindowListCreateImage` 截真实窗口后**数指定颜色的像素**，
> 以及在拖动事件上记录 `ProcessInfo.processInfo.systemUptime - event.timestamp`
> 得到"事件处理滞后"。这两个指标合起来就能把"跟手不跟手"变成数字。


### 为什么不用 PDFKit 自带的 `isInMarkupMode`

它在 macOS 26 已废弃，且会带来一整套自己的编辑手势，与「空格抓手」「⌥+滚轮缩放」两个全局监听
抢事件；它也不区分标注类型，高亮会被一起拖走。

### 右侧属性栏

点选一条标注 → 右侧出现属性栏：

- **颜色 / 背景色**：8 色调色板 + 自定义取色器 + **「透明」**（斜线圆点，完全不上色）。
  对文本注释这一项是**背景色**。
- **文字颜色**：只在选中文本注释时出现，和背景色分开。
- **不透明度**：0~100% 滑条。
- **线宽**：涂鸦 / 矩形 / 圆 / 直线 / 箭头才有。连续滑条 + ± 手动加减 + 粗细预览。
- **字体**：只在选中文本注释时出现。族菜单 + 字号滑条 + 加粗 / 斜体。
- 「框适应内容大小」（文本注释）与删除。

所有修改**即时生效**。取色后会统一转到 sRGB —— 否则和调色板里的颜色比对时会因为色彩空间不同
而同时显示两个"当前颜色"。

**工具条上也有同一套控件**（只读/编辑切到编辑模式才出现）：颜色 → 不透明度 → 线宽/字体。
选中了标注时改这些，会**同时套到那条标注上**；没选中就是"下次画的时候用这个样式"。
这些设置写进 `UserDefaults`，下次打开还是上次的颜色和线宽。

> 工具条比早先宽了不少（多了不透明度、字体、直线），所以**样式那一段是横向可滚动的** ——
> 窗口拉窄了也能取到最右边的控件，不会把工具按钮挤出去。

> ⚠️ **属性栏里的控件必须能收缩宽度。** 早先它们用固定宽度（字体那一行加起来约 300 点），
> 超过栏宽（默认 260、最小 200）时 SwiftUI 会把容器撑大，`.frame(width:)` 就被架空了 ——
> 表现是**拖分隔条没反应**、内容还被裁。现在滑条统一走 `sliderWidth: CGFloat?`
> （nil = `maxWidth: .infinity`），字体控件在属性栏里**分两行**（族一行、字号+B/I 一行）。

也可以从左侧「批注」列表选（列表里能选到高亮/下划线这类不方便在页面上点的标注）。
**列表里选中的那条会用强调色高亮**；另外当前页的标注还有一层很淡的底色，那是"它在当前页"
的意思，和"选中"是两回事（早先只有后者，导致同页有多条时分不清选的是哪条）。
属性栏与搜索结果共用右侧这一栏：都有时上下排，属性栏在上。

> 只读模式下，制作类操作（新增/拖动/删除/写回）全部禁用；阅读功能（朗读、自动滚动、
> 缩放、搜索、跳转）不受影响。

## 打印

⌘P（或工具栏「更多 → 打印…」）先打开**打印设置面板**，再进系统打印面板。两个面板分工明确，不重复设置：

- **「打印设置」面板负责**：页面范围、**纸张大小与方向**、缩放、自动旋转、每张纸页数（拼版）、是否打印批注
- **系统打印面板负责**：选择打印机、份数、最终预览

选「跟随系统」纸张时，纸张与方向仍留给系统面板处理（比如打印机里装的是别的纸，还有办法改）。

**面板右侧是实时预览**：改任何设置都会重新合成预览（带 250ms 防抖，因为拼版可能较慢），
拼版效果、页面范围、批注开关、**换纸张后的版面**都能先看到再打印。

> **预览保证整页可见。** PDFKit 的 `autoScales` 在连续模式下只保证**宽度**放得下，
> A4 这类竖长页面就会"一整页显示不全、要上下划"。
> `PageFittingPDFView` 自己算一个让**每一页**都完整可见的缩放（取所有页里最难的
> 那一页所需的缩放），结果是一屏正好一页，滚一下翻一页。
> 实测同一视口下：默认 `autoScales` 渲染出 409 × 530（超出 520 的视口高度，必须滚动），
> 换成整页适配后是 389 × 504，完整放得下。

> 预览和实际打印**调用同一个** `PDFPrintService.makePrintableDocument`，
> 从结构上保证"预览看到的就是将要打出来的"。
> 这是刻意的设计 —— 如果预览另写一套合成逻辑，两边迟早会分叉。

**实现要点**（改动前先看 `PDFPrintService.swift` 的注释）：

- **所有"非整份原样打印"的需求，都先合成一份临时 `PDFDocument` 再交给 PDFKit。**
  因为页面范围可能不连续（`NSPrintOperation.pageRange` 只支持连续区间）、还要剔除批注、还要拼版，
  走同一条"重建文档"的路径比分别处理简单得多。只有"全部页 + 不拼版 + 保留批注"才直接用原文档
  （保留文档级元数据与链接，且零开销）。
- **剔除批注必须先 `page.copy()` 再做**，否则会改到**原文档**的页面（已用探针专门验证过：副本清空、原文档一字未动）。
- 拼版用 `CGContext` 生成新 PDF：按 `rows × columns` 布局，每格等比居中绘制，另画裁切线；
  纸张尺寸由用户在面板里选的纸张 + 方向决定。
- 自定义缩放没有对应的 `PDFPrintScalingMode`，改用 `NSPrintInfo.scalingFactor` 叠加。
- 设置纸张时 `paperSize` 始终按**纵向**写、方向另设 `orientation`，
  避免设置成"已旋转的尺寸"再叠一次方向。
- 预览用的 `PageFittingPDFView` 是独立实例，不绑定 viewModel；缩放/抓手的全局事件监听会检查事件所在窗口，
  sheet 的窗口与之不同，所以不会误触发主视图的缩放与平移。

### 🛑 打印需要沙盒打印权限（v1.3.13 修的）

**沙盒应用要调 `NSPrintOperation`，必须在 entitlements 里声明 `com.apple.security.print`。**

缺这条时的表现极具误导性 —— 代码一行没问题，`operation.run()` 也照常被调用，
但系统打印子系统会**直接拒绝**，并弹出：

> **此应用程序不支持打印。**
> 请联系应用程序开发者。

（英文版是 "Printing Not Allowed / This application is not allowed to print."）

这不是"打印失败"，是**权限没声明**。沙盒里打印没有别的合法绕法，只能声明。
本项目早期就漏了这条 —— `app-sandbox` 开着，打印权限一直是缺的。

取证方式（改完/构建后自查）：

```bash
# 看已构建 app 的真实签名，必须同时出现这两条
codesign -d --entitlements :- "…/PDFReader.app"
#   com.apple.security.app-sandbox  → true
#   com.apple.security.print        → true   ← 缺它就会弹上面那个窗
```

在 Xcode 里的对应开关是 **Signing & Capabilities → App Sandbox → Hardware → Printing**，
勾上就等于写进 `PDFReader.entitlements`。本项目用的就是后者（手写文件，工程通过
`CODE_SIGN_ENTITLEMENTS` 引用），**改完 entitlements 要重新构建运行才生效**。

> 顺带一个坑：`entitlements` 文件里的 XML 注释**不能出现连续两个短横线 `--`**，
> 否则 `plutil -lint` 会放过、但签名器的 `AMFIUnserializeXML` 会报
> `syntax error near line N`。分隔线用 `===` 别用 `---`。

### 🎯 打印走的是**我们自己的渲染器**（v1.3.15）

批注在屏幕上是自绘的，但**打印走 PDFKit 的渲染** —— 它按 `/LE` 画出一个**平底三角**，
和屏幕上的倒钩箭头对不上，用户看到的就是"预览一个样、打出来另一个样"。

**文件层面没有出路**，两条标准路都实测堵死了：

| 尝试 | 结果 |
|------|------|
| `/Polygon` + `/Vertices` | `PDFAnnotationSubtype` 里**根本没有 `.polygon`**；硬造出 `/Polygon` 后 PDFKit 报 `Unhandled annotation subtype`，且 **`/Vertices` 被丢弃**，连写进文件都做不到 |
| `/Ink` + `/IC` | `/IC` **能**写盘，但 PDFKit 渲染时**只描边、不填充**（实测填充像素 = 0） |

于是走渲染侧：实测 **PDFKit 会调用 `PDFAnnotation` 子类 override 的 `draw(with:in:)`**
（`page.draw(with:to:)` 与 `thumbnail` 两条路径都验证过）。打印前把自绘批注
**换成 `SelfRenderedAnnotation` 代理**，PDFKit 就用屏幕上同一套渲染器画。

**只在内存里的副本页上替换** —— 原文档、写盘内容、文件格式都不动。
代理的 `bounds` 取 `renderedBounds(of:)`（自绘形状包围盒外扩半个线宽 + 2pt），
免得 PDFKit 按原来看起来更小的 `bounds` 把箭头尖端裁掉。

> ⚠️ 替换顺序：**先给"我们不接管的 ink"校正 `/Rect`，再做替换**。
> 替换后绘制不再依赖 `bounds`；反过来的话，校正会平移 `bounds.origin`，把已接管的 ink 画歪。

验证（`/tmp/polyprobe/print`，编入真实源码跑完整打印管线）：

| | 打印出来的形状 |
|---|---|
| 旧行为（`shouldDisplay = true` 交给 PDFKit） | 平底三角，线条平头截断、与三角之间有缝 |
| 新行为（换成自绘代理） | **倒钩箭头，与屏幕同源** |

红像素 24412 / 25224、差异 1724 —— 形状确实换了。对比图见项目根目录
`打印箭头-修复前后对比.png`。

> **别的阅读器打开时仍是平底三角** —— 文件里存的是标准 `/Line` + `/LE`，它们按 PDF 规范画。
> 这是**正常的兼容行为**（别家能打开、能选中、能编辑），不是缺陷。
> 要连这一半也统一，只能把箭头画进**页面内容流**（= 放弃批注语义），代价见「已知限制」。

## 批注列表（侧边栏「批注」面板）

- **跳转**：单击一条 → 跳到那一页并选中它
- **多选**：`Cmd + 点击` 逐条加选/取消，`Shift + 点击` 选一段范围
- **删除**：选中（可多选）后按 **`Delete` / 退格键**，或点工具栏顶部的「删除选中的 N 条」，
  也可以右键选「删除」。确认弹窗会列出将删的内容（超过 8 条时只列前 8 条 + 总数）
- **单击是跳转、多选不跳转**：批量操作时不该把页面拽来拽去

### 选中时列表不整体重绘（v1.3.17）

点一条批注会触发两轮视图更新、整列表跟着重绘一遍 —— 肉眼就是"闪一下"。三处根因：

| 问题 | 改法 |
|------|------|
| 行没有相等性判断，选中任意一条都要把**每一行**重新求值（每行还带一个 `contextMenu`，要建 `NSMenu`） | `AnnotationRow` 实现 `Equatable` + `.equatable()`，没变的行直接跳过 |
| 行底色画在 `listRowBackground`（List 层）—— SwiftUI 判断不出"只有这一行的背景变了"，于是整列表重算 | 底色收进 `AnnotationRow` 内部（受 `Equatable` 保护）；List 侧只留一个**常量** `.listRowBackground(Color.clear)` 用来清掉系统底色 |
| `isRowSelected` 同时读 `selection` 和 `viewModel.selectedAnnotation` —— 点一行前后触发两轮 | 只看 `selection`；页面点选经 `onChange` 同步进来，晚一帧但省掉一整轮 |

顺带去掉两处无谓赋值：`select()` 里已经是同一条批注就不再写 `selectedAnnotation`，
`goToAnnotation()` 里页码没变就不再写 `currentPageIndex`。这两个都是 `@Published`，
写一次所有观察者（列表 / 属性栏 / 调色板 / 工具栏）各重绘一轮。

> ⚠️ `AnnotationRow.==` 里**不能只比 `item.id`**：`id` 是 `ObjectIdentifier(annotation)`（对象身份），
> 批注内容被改时它纹丝不动，只比 id 的话列表会停留在旧文字上。内容、日期、页码都得一起比。

### "当前页"标记的判据改成视口中心（v1.3.19）

**症状**：点列表里某条批注，那一行的"当前页"竖条亮一下，随即消失，而且不会自己回来。

**根因**（探针 `/tmp/pageprobe` 实测：真 PDFView + 8 页文档 + `.singlePageContinuous`，
也就是本 app 的显示模式）：

`PDFViewModel.syncState()` 每 0.3 秒用 `pdfView.currentPage` 反推页码，而
**`currentPage` 只跟着 PDFKit 自己那套滚动路径更新**。直接操作内部 `clipView` 之后它一点不变：

| 操作 | `pdfView.currentPage` | 视口中心页 `page(for:nearest:)` |
|------|----------------------|------------------------------|
| `centerOn`（直接滚 `clipView`） | **停在旧页**：强制 `layout`/`display` 不变、窗口可见且是 key 窗口也不变、等 2 秒仍是旧页 | 正确（目标页） |
| `go(to:)`（PDFKit 自己的导航 API） | 正确 | 正确 |

而 `centerOn` 走的正是"直接滚 `clipView`"这条路（`PDFView.go(to:)` 定位不到视图正中）。
于是跳转后：我们刚把 `currentPageIndex` 设成目标页（竖条亮起），0.3 秒后这个轮询用
**没更新的** `currentPage` 把它冲回旧页 —— 竖条随即消失，且不会自己回来。

**修法**：`syncState()` 改读**视口中心页**，和 `centerOn` 用同一套判据。
`centerOn` 把目标点摆到视口正中，目标页必然包含视口中心，两边永远一致。

验证（6 个跳转场景，含首页 / 末页被 `constrainBoundsRect` 夹紧的情形）：

| 批注位置 | 目标页 | 旧判据 | 新判据 |
|---------|--------|--------|--------|
| 第 4 页 · 页中央 / 页顶 / 页底 | 第 4 页 | 第 1 页 ❌ | 第 4 页 ✅ |
| 第 2 页 · 页中央 | 第 2 页 | 第 1 页 ❌ | 第 2 页 ✅ |
| 第 1 页 · 页顶（夹紧） | 第 1 页 | 第 1 页 | 第 1 页 ✅ |
| 第 10 页 · 页底（夹紧） | 第 10 页 | 第 1 页 ❌ | 第 10 页 ✅ |

> ⚠️ 早先两次探针都没查出这个：一次用的是 `go(to:)`（那条路 `currentPage` 是更新的），
> 一次视口小到一屏装不下一页（那时 `currentPage` 和中心页恰好一致）。
> **探针的配置必须贴近真实使用** —— 本 app 是 `singlePageContinuous`，
> 常见情形是一屏能看到上下两页，也正是两者分叉的时候。

### 跳转与"当前页"标记落在同一次更新里（v1.3.18）

点一行要同时做两件事：刷新选中配色、把"当前页"竖条挪过去。
一开始跳转写在 `.onChange(of: selection)` 里 —— 而 `onChange` 的语义是
"状态改完、视图更新**之后**"才回调，也就是**下一帧**。于是点一行会看到两次更新。
现在跳转写进 `Binding` 的 `set`（`listSelection`），两件事落在同一次更新里。

（这一条本身是对的，但它**不是**"竖条出现后又消失"的原因 —— 真正的原因是上面那条判据不一致。
两个都改完才是现在的结果。）

### Delete 键：靠键盘监听转发，不靠列表的 `.onDeleteCommand`（v1.3.19）

`EditablePDFView` 挂了一个 `NSEvent.addLocalMonitorForEvents` 的**全局**键盘监听，
它跑在所有键盘事件最前面，并且会在 Delete 键上**直接吞掉事件**去删单条 ——
所以列表自己的 `.onDeleteCommand` 曾经永远收不到事件（"选了三条只删一条"）。

第一版改法是"多选时放行、让事件走到列表"，**实测无效**：
`.onDeleteCommand` 需要**列表拿到焦点**才触发，而焦点一般在 PDF 视图那边，
按 Delete 毫无反应 —— 放行只是把事件交出去，没人接。

现在改成**监听主动转发**，完全不依赖焦点：

1. 列表把选中条数写进 `viewModel.annotationListSelectionCount`；
2. Delete 键 → 监听看到列表里有选中，就把 `listDeleteRequestTick` +1 并吞掉事件；
3. 列表 `onChange(of: listDeleteRequestTick)` → 这时才拿得到"选的是哪几条" → 走统一确认弹窗。

只有一种情况仍走原来的直接删除：列表只选中一条、且页面上也正选着它（那种直接删更顺手）。
`.onDeleteCommand` 保留一份作兜底，两处共用同一个确认弹窗、不会重复触发（监听会吞掉事件）。

> ⚠️ `annotationListSelectionCount` **故意不是 `@Published`**：它由列表 `Binding` 的 `set`
> 在**视图更新过程中**写入，`@Published` 在那个时机赋值会触发 SwiftUI 的
> "Publishing changes from within view updates" 警告，更新本身还有被合并/丢弃的风险。
> 它也只被键盘监听（非渲染路径）读取，不需要触发重绘。

### 列表空的时候也必须能保存（v1.3.20）

「保存批注到 PDF」有两条入口：侧边栏按钮，和菜单里的 ⌘S（`NotificationCenter`）。
按钮原来挂着 `.disabled(viewModel.annotations.isEmpty || !viewModel.isEditable)`，
而 **⌘S 那条路只看 `isEditable`** —— 两条路条件分叉，长出这么一个坑：

**把最后一条批注删光之后，列表是空的，按钮就点不动了** —— 而那恰恰是最需要保存的时候
（要把"删除"写进文件）。只有 ⌘S 能救。

修法是把按钮的判据对齐到 ⌘S：**只要求可编辑**。列表空的时候也允许存：
多存一次只是把同样的内容重写一遍（写前照例自动备份），而"该存时存不了"是实打实的坑。
列表为空时下方也补了一句话点明这件事。

端到端验证（探针 `/tmp/saveprobe`，**编入真实的 `PDFViewModel`**，走
`bind → applyDisplayPolicy → removeAnnotations → saveAnnotationsToDisk`）：

| 步骤 | 结果 |
|------|------|
| 打开 3 条批注（高亮 P1、方块 P2、涂鸦 P2） | 列表 3 条，自绘策略把 3 条设成 `shouldDisplay=false` |
| 全部删除 | 列表 0 条；**文件里仍是 3 条**（还没写盘，符合预期） |
| **空列表时保存** | ✅ 不抛错；备份落在原文件旁（`besideOriginal`） |
| 重新打开文件 | 用户批注 **0 条** → 删除确实写进了文件 |
| 打开备份 | **3 条** → 删之前的原样还在，可回退 |

> 一个观察：空列表保存时 PDFKit 会打一条内部日志
> `Could not sync appearance dictionary. We need to have access to the PDFPage…`。
> 它不是我们代码发的（`appearanceOverride` 全项目 grep 不到），也不影响写盘
> （文件重开校验通过）。用四种组合做对照都没能稳定复现它 —— 只有在主场景才出现。
> 结论：**PDFKit 内部日志，无害**；写盘结果已单独校验。

> ⚠️ 注意 `annotations.isEmpty` 不是"没有东西可存"的正确判据。真正的语义是
> "有没有未保存的改动"。本项目没有 dirty 标记，所以退一步用"可编辑"当条件 ——
> 这比用"列表非空"安全得多。

### 整行底色只表示"选中"（v1.3.16）

改之前列表里有**三种**整行底色，看起来就是"有的浅蓝、有的白、选中的深蓝"：

| 状态 | 旧底色 | 现在 |
|------|--------|------|
| 选中 | `accentColor` 22% | **唯一的整行底色**，值降到 **12%**（v1.3.25） |
| 在当前页 | `accentColor` 7% | **改成行内左侧的细竖条** |
| 其它 | 透明 | 透明 |

> **文字色不能跟着选中变强调色**（v1.3.25 修）：强调色底 + 强调色文字 = 蓝底压蓝字，
> 标题糊得看不清（用户在目录面板报的就是这个）。现在三个列表统一成
> **底色 12% + 文字一律 `.primary`**，选中靠底色表达就够。

问题不在颜色数值，在于第二行**「当前页」根本不该用整行底色**：
它是**跟着翻页自动变**的，用户什么都没选，列表里却飘着一片浅蓝；
而它和"选中"用的是**同一套视觉语言**（整行蓝底），
于是用户分不清"我选中的"和"恰好在这一页的"。

现在「当前页」用一根 3pt 竖条表示：不抢整行底色，翻页时也能一眼看出这页有哪些批注。

> 两个实现要点：
> - 整行底色交给 `listRowBackground`（而不是行内 `.background`）—— 它能盖掉系统默认的
>   选中底色，避免"系统一层 + 我们一层"叠成更深的蓝。
> - `List(selection:)` 那一层**不能再挂 `onTapGesture`**：它会吃掉点击、让 List 收不到
>   选择事件，多选就永远触发不了。「点了就跳转」因此改由 `Binding` 的 `set` 承担
>   （见上面 v1.3.18 那节）。

## 目录（侧边栏「目录」面板，v1.3.23）

**能编辑**：新增（目标 = 当前页）／**用页面上选中的文字新增**（标题取选中文字，目标点记的是
选区左上角，点目录会正好落在那一行）／改名／删除（连同子项）／**降级·升级**（层级）／
**拖动改顺序与层级**（v1.3.25）／把目标改成当前页。单击条目即跳转。

改动**不会自动写盘**（v1.3.28 改的，原因见「保存与备份」）：
按 ⌘S 写入，或者关闭文档时它会问你一句要不要保存。有未保存改动时标签页上有小圆点。
（可在「设置」⌘, 里关掉，改用 ⌘S。）

### 拖动：按住行尾那一块拖（v1.3.25 加，v1.3.26 修，v1.3.27 定型）

**按住行尾的「第 N 页 + ⠿」那一整块拖动** —— 不是按住标题拖。
落点按行内**纵向位置**分三段：

| 落在行内的位置 | 效果 |
|---------------|------|
| 上 35% | 放到这一行**前面**（同级） |
| 中间 30% | 放进这一行**里面**（成为它的子项） |
| 下 35% | 放到这一行**后面**（同级） |

落点用横线（前/后）或描边（里面）提示。右键菜单里另有「上移／下移」作为备用通道。

### ⚠️ 这个功能前后踩了四层坑（都记在这，别再往回改）

**第 1 层：`onDrag` 不能挂在整行上。**
在 `List` 的行上挂 `onDrag`，它会和 List 自己的选择手势打架：
单击要等"这不是拖拽"判定失败才轮到选择（**第一次点没反应**），
而起手又要求落在整整一行里，稍移出去就取消（**大部分拖不动**）。
所以拖拽手势只挂在行尾那一块上；起手之后**拖到哪儿都行**（会话已交给系统）。

**第 2 层：拖拽热区不能只有那个小图标。**
一开始热区只有 18pt 的图标，按偏一点点就完全起不了拖 —— 表现就是"有时候能拖、大部分拖不动"。
现在热区是「页号 + 把手」整块（约 66×22）。

**第 3 层：`List(selection:)` 会画系统自己的选中态，而且清不掉。**
用 selection 绑定时 macOS 会在行上**另外画一层强调色实底 + 白字**，
`listRowBackground` **清不掉它** —— 结果我们自绘的浅底和系统的深蓝实底会同时出现在不同行上，
看着像"突然冒出一个蓝条"（用户截图里两行同时高亮就是它）。
现在**不给 List 传 selection**，选中完全由行内自绘（点击用 `onTapGesture`）。
键盘 Delete 不受影响：主路径一直是全局键盘监听转发。

**第 4 层：拖拽提示每变一次，整列表都要重绘。**
每行都挂着 `contextMenu`（重建要构造 NSMenu），而拖拽时落点提示变化非常频繁 ——
叠加起来就是"一顿一顿 / 卡卡的"，**而且这种重绘还可能把正在进行的拖拽会话打断**
（表现就是"突然又拖不动了"）。修法：

- 行抽成独立类型 + `.equatable()`，只在**自己这一行**的显示真的变了时才重新求值
  （`contextMenu` 也因此必须建在行 body 内部，建在外面就拦不住它重建）；
- 拖拽提示**按需构建**，不再"常驻 + `opacity(0)`"；
- `validateDrop` 不依赖"谁在拖"这个状态（只看载荷类型）—— 两者谁先执行没有保证；
- "谁在拖"用**引用类型**存而不是 `@State`（后者在 `onDrag` 里写会触发重算）。

**另外：提示线要有自清理。** 正常落在某行时 `performDrop` 会清、
换行时 `dropExited` 会清，但**按 Esc 取消**和**拖到列表外松手**这两种情况没有任何回调，
提示线就留在画面上了。现在多一个看门狗：提示一出现就每 0.12 秒看一眼
`NSEvent.pressedMouseButtons`，鼠标松了就补一次清理（拖拽期间不写任何状态，不引起重绘）。

> ⚠️ **环检测在 viewModel 层，不在界面层**：`moveTOCEntry` 会拒绝"拖到自己身上"和
> "拖进自己的子孙里"。这两种落点在界面上看不出任何异常，但一旦放进去，节点就成了自己的祖先 ——
> 之后**任何一次遍历都会无限递归**，表现是"目录整个消失 / 界面卡住"。
> 所以宁可什么都不做（实测：两种情形都返回 false 且树不变）。
>
> 另一个坑是**索引偏移**：必须先 `removeFromParent()` 再取目标的 `index`。
> 反过来（先算下标再摘）会让"往后同级移动"多挪一位 —— 实测 `X` 拖到 `Y` 后面会变成
> `Y Z X` 而不是 `Y X Z`。

### 目录面板的配色：整行底色只表示"选中"

选中行原来是**强调色底（22%）+ 强调色文字**，蓝底压蓝字，标题糊得看不清（用户原话）。
现在改成和批注列表、书签列表**同一套**：底色 `accentColor.opacity(0.12)`，文字一律 `.primary`。
—— 三个列表统一成一个值，别再各写各的。

### ⚠️ PDFKit 完全写不了目录 —— 所以自己往文件里注入

实测（`/tmp/tocprobe`，每一条都跑过）：

| 尝试 | 结果 |
|------|------|
| 本没有目录的文档，自建树设进 `document.outlineRoot` | 内存里正常，`write` 返回 true，但**文件里没有 `/Outlines`** |
| 换成"先 assign 空 root 再插子项"、或看 `dataRepresentation()` | 一样没有；子项的 `document` 恒为 nil（**PDFKit 不"收养"程序化插入的目录项**） |
| `PDFActionGoTo` 代替 `PDFDestination` | 一样写不进去 |
| **改一个已存在的目录**（手工造的带目录 PDF，PDFKit 能正常读出两层） | 改名／加子项／删项在内存里都对，写盘后重开**还是原来的标题** —— 改动被丢弃 |

读没问题，写完全没有。所以 `PDFOutlineWriter` 自己动手，用**增量更新（incremental update）**：
**原始字节一个都不动**，只在文件末尾追加

1. 目录树对象（`/Type /Outlines` + 各项 `/Title /Parent /Dest /First /Last /Next /Prev /Count`）
2. 一份**新的 catalog**（复制原来的字典，把 `/Outlines` 换成我们这棵；目录删光时是**去掉这个键**）
3. 一段**新的 xref 段**（只列新对象）+ trailer（`/Root` 指向新 catalog、`/Prev` 指回原 xref）

这是 PDF 规范认可的标准做法，比"整份重写"安全得多。

**只处理 PDFKit 刚写出的文件**（调用时机固定在 `document.write(to:)` 之后，所以结构永远是
PDFKit 自己那种规矩形态）：经典明文 xref 表、没有对象流、catalog 与页对象都是明文。
任何一条不满足就**直接放弃**（抛错），绝不冒险写。解析时还要**沿 `/Prev` 链读各段 xref**
（不跟就会在"连续保存两次"时报"xref 里没有对象 N"）。

**写完先自检、再落盘**：用 `PDFDocument(data:)` 重新打开，要求页数一致、目录树能原样读回、
抽样页面的**文字与注入前完全相同**。任何一条不过就丢掉结果、保留原文件。
注入失败**不算保存失败**（批注确实已经写进去了），用 `outlineWriteNotice` 单独如实告知。

### 别的软件能看到吗 —— 用独立实现验证过

不能只用 PDFKit 自己验（那等于自证）。用 **pypdf**（Python 的另一套独立实现）读 app 真实保存流程
产出的文件，能完整读出中文标题、两层嵌套和目标页：

```
· 第一章 绪论 → 第 1 页
    · 1.1 研究背景 → 第 2 页
· 第二章 方法 → 第 4 页
· 第 5页的标题文字 → 第 5 页
```

### 一个如实记录的观察

在**很长的一段操练历史**之后（多次保存 + 撤销换页 + 注入），PDFKit 自己写出的 xref 表里
出现过一条 `偏移 0 / 类型 n` 的坏条目（pypdf 会打一行
`Ignoring wrong pointing object 7 0 (offset 0)` 然后自行恢复，内容全部读得出来；PDFKit 也照常打开）。

- 已用 7 种受控场景（反复写／注入／换页／换页+注入／多轮交替／批注删除后保存／撤销后再保存）
  逐个排除：**都不是我们的注入造成的** —— 我们的注入只写 `X 1` 这种子段，
  而那一段坏条目出在 PDFKit 写出的 `0 N` 全表里。
- 影响有限（读者会扫描恢复），**不去修它**（改 PDFKit 的 xref 反而更危险）。

## 撤销与重做（⌘Z / ⇧⌘Z，v1.3.21）

覆盖范围：**新增**（高亮/下划线/删除线、拖拽绘制的图形、便签、文本注释、签名）、
**删除**（单条 / 批量算一步）、**改样式**、**拖动移动**、**框适应内容**、
**批量修复被裁切的文本注释**（整批算一步）。

### 做法：以"页"为粒度的快照，而不是逐条记反操作

改动前先把**被碰到的那几页整页留一份 `PDFPage.copy()`**；撤销就用它把那一页换回来。

为什么不写"每个操作的反操作"：改批注的路径有十来处（文字选区、拖拽绘制、便签、文本注释、
签名、改样式、拖动、删除、框自适应、批量加高…），**手写十来个反操作，漏一处就是"撤销之后
状态不对"**，而且以后每加一个改动路径都得记得补一个。整页快照对所有改动一视同仁。

四个前提都实测过（探针 `/tmp/undoprobe`）：

| 前提 | 实测结果 |
|------|---------|
| `PDFPage.copy()` 是不是深拷贝 | ✅ 副本里的批注是**独立对象**，两边增删互不影响 |
| 换页后再写盘是否正确 | ✅ 页序 / 页数 / 批注内容都与目标状态一致 |
| `copy()` 的成本 | ✅ 近乎为零（页面内容惰性共享：50 次 copy <1ms、常驻内存 +0.0MB） |
| 换页会不会让视图跳动 | ✅ **不跳**：`clipView.origin` 与"视口中心页"偏移 **0.0** |

> 换页用的是**先插新页、再删旧页**（`insert(_:at:)` + `removePage(at: index+1)`），
> 不是 `removePage` 再 `insert` —— 后者中间有一小段"那一页被摘下来"的窗口，
> PDFView 可能正好这时去画它，日志里会刷
> `Drawing a PDFPage when its PDFDocument is nil is unsupported.`
> （改成先插后删能少掉大部分；探针里偶尔仍会看到一条，属 PDFKit 内部日志，不影响结果：
> 视图不跳、写盘正确、无崩溃。）

### 两个必须注意的点

1. **换页会换掉整页的 `PDFAnnotation` 对象** —— 侧边栏的 id 是 `ObjectIdentifier(annotation)`，
   所以撤销后必须 `reloadAnnotations()` 重新解析，并把 `selectedAnnotation` 清掉
   （旧引用已经不在文档里了）。`applyPageSnapshots` 就是这么做的。
   > 探针里我就踩到过：拿着 undo 之前的旧对象去改样式，改的是个游离对象，界面上当然没反应。
2. **拖动要记的是"拖动前"的状态** —— 所以快照在**按下时**就拍好暂存，
   抬起来时只有真的移动过才入栈。只是点一下选中不该凭空多出一个"移动批注"的撤销步骤。

### ⌘Z 与文本框的冲突

编辑菜单里那对系统默认的"撤销/重做"在本 app 里原本是**死的**（没有任何响应者实现 `undo:`），
所以用 `CommandGroup(replacing: .undoRedo)` 换成了自己的。
但**搜索框、便签/文本注释输入框里的 ⌘Z 必须留给文字** —— 菜单动作先看焦点在不在
`NSTextView` 上，是就把标准 `undo:` 交回响应链。

> ⚠️ 这里要**显式判断焦点**，不能靠"`sendAction(undo:)` 返回 false 才兜底"：
> `NSWindow` 自己也可能接住 `undo:`，那样批注撤销就永远轮不到。

### 一个 SwiftUI 的坑（顺手记下）

`PDFContentView` 那条 `.onReceive` 链本来就有 14 个菜单指令，加上撤销/重做后编译器直接报
`unable to type-check this expression in reasonable time`。拆成
`sheetHost` / `readCommands` / `editingCommands` 三个计算属性（每段 ~8 个）就好了。

## 书签栏（侧边栏「书签」面板，v1.3.22）

- **跳转**：单击一条 → 跳到那一页
- **多选**：`Cmd + 点击` 逐条加选/取消，`Shift + 点击` 选一段范围
- **删除**：选中（可多选）后按 **`Delete` / 退格键**，或点面板底部的「删除选中的 N 条」，
  也可以右键选「删除」。多选时弹确认框，只选一条就直接删（和行尾那个 ✕ 一致）
- **单击是跳转、多选不跳转**：批量操作时不该把页面拽来拽去

**删除与编辑模式无关**：书签是应用自己的数据（存在 `UserDefaults`），不是文档里的批注 ——
只读模式正是看书签的时候，所以 ⌘Z 那套"要可编辑"的限制不适用于它。
`EditablePDFView` 的键盘监听里，书签那一支排在 `isEditable` 判断**之前**。

### 配色语义和批注列表统一

原来「当前页的那条书签」用整行 `accentColor` 12% 铺底，和"选中"是同一套视觉语言 ——
和批注列表当初那个问题一模一样（见上面 v1.3.16 那节）。现在：

| 状态 | 表现 |
|------|------|
| 选中 | 整行 `accentColor` 22%（**唯一的整行底色**） |
| 当前页 | 行内左侧 3pt 竖条 |

### 「删了书签，工具栏图标还亮着」（v1.3.22）

根因有两层，都修了：

1. **书签栏原来直接调 `BookmarksStore.shared.remove(...)`**，绕过了 viewModel ——
   `isCurrentPageBookmarked` 没人重算，工具栏那个图标就一直是旧状态。
   现在统一走 `viewModel.removeBookmarks(ids:)`。
2. **`goToPage(at:)` 也不刷新书签状态**：它只写 `currentPageIndex`，而 `syncState`
   只在"页码**变了**"时才更新书签状态 —— 等 0.3 秒后的轮询跑到时 `index == currentPageIndex`，
   那一支根本不进来。表现是从缩略图跳到某页后，图标显示的还是**上一页**的状态。
   现在 `goToPage` 末尾显式调一次 `updateBookmarkStatus()`。

> ⚠️ 兜底用的是**"书签已改完"的通知**（`BookmarksStore.save()` 里发
> `.pdfBookmarksDidChange`），**不是** `BookmarksStore.$bookmarks`：
> **`@Published` 是在 willSet 里发通知的** —— 收到那一刻数组还是旧的，
> 拿它去算"当前页有没有书签"只会算到改动**前**的状态（等于没刷新）。
> 用通知还有个好处：天然支持多个观察者（每个标签页一个 viewModel）。

### Delete 键的路由（与批注列表共用同一个键盘监听）

`EditablePDFView` 那个全局监听现在分两支：**书签栏有选中就删书签**，否则按批注那套走。

> ⚠️ 两个列表都可能留着一个"选中数"在 viewModel 上，而侧边栏切面板时视图会销毁、
> **计数不会自己归零**。不清的话会出现：选中批注 → 切到书签栏 → 按 Delete 什么都不发生
> （事件被吞掉了，而那个列表已经不在了）。所以两个侧边栏都在 `onDisappear` 里清自己的计数。

## 保存与备份（v1.3.25 重构，v1.3.28 改成"关闭时提醒"）

### 三条写入时机

| 触发 | 备份 | 说明 |
|------|------|------|
| **⌘S /「保存批注到 PDF」** | 按设置（默认备份） | 主要方式 |
| **关闭文档 / 退出时提醒** | 同上 | 有未保存改动才问：「保存 / 不保存 / 取消」 |
| **改动后自动保存**（**默认关**） | 不产生备份 | 目录改动后防抖 0.8 秒 |

### 为什么自动保存默认关掉了（v1.3.28）

**它会卡。** 写盘是**同步的整份序列化** —— `PDFDocument.write` + 注入目录 +
**重新打开自检** + 原子替换，全在主线程上跑。文件一大就是几百毫秒的停顿；
而防抖只有 0.8 秒，在目录里连续改几下就会反复触发 —— 手感上就是"一顿一顿"。

现在改成默认「**关闭时提醒保存**」，由用户自己按 ⌘S，或者在关闭文档时统一决定。
想开着自动保存也可以（设置里有），代价如上，设置界面里写明了。

### 脏标记：靠一条漏斗覆盖所有改动

提醒保存的前提是"知道有没有改过"。这里**没有**去每个调用点手工置位 ——
那样迟早漏一个，表现就是"改了却没提醒"。

置位只走三条路：

| 路径 | 为什么一处就够 |
|------|----------------|
| ① **批注改动** | 十来个改动路径（文字选区高亮、拖拽绘制、便签、文本注释、签名、改样式、拖动、删除、框自适应、批量加高）**全都经过 `recordUndo`** —— 撤销快照的总入口 |
| ② **目录改动** | 全都经过 `outlineDidChange`（7 个改动方法各挂一处） |
| ③ **撤销 / 重做本身** | 它换掉整页，同样是改文档 |

清位在 `writeDocument` 成功之后 —— 自动保存和手动保存共用同一条写入路径，所以只有一处。

> 交叉核对过：`notifyAnnotationsChanged` 的 10 处调用全部落在上面这三条覆盖范围内
> （其中 4 处共用 `attach` 这个"新增批注"的漏斗）。
>
> 有未保存改动时：**标签页标题旁会出现一个小圆点**，目录面板底部也会写一句。

### 三个"看着很轻、其实会卡"的地方（v1.3.29）

**① 脏标记不能做成 `PDFViewModel` 上的 `@Published`。**
观察 `PDFViewModel` 的视图有一大票（PDF 视图、缩略图栏、批注栏、工具条、调色板…）。
把这个标记做成它的 `@Published`，**每次置位/清位都让这一整票视图重算 body** ——
用户实测的"改一下目录就顿一下"里就有它。

现在拆成独立的小对象 `UnsavedChangesFlag`，订阅面收窄到只有两处：
标签页那个小圆点、目录面板底部那句提示。

**② `isEditable` 的 `didSet` 里不能接着改别的 `@Published`。**
`didSet` 是在 **SwiftUI 写入绑定的同一轮更新里**执行的 ——
在里面改右栏显隐、清选中项，就落到"视图更新过程中改状态"那条禁忌上，
SwiftUI 会把这一次更新**丢掉**。症状正是：**点了「编辑」，按钮变色了但没切过去，要再点一次**。

改成把副作用挪到下一轮主队列：状态切换立刻生效，右栏随后跟上。

**③ 自动保存写盘前要看一眼鼠标按没按着。**
写盘是同步的整份重写，插在用户"拖动一半"中间就是明显卡顿
（"拖完目录要卡几秒才能继续拖"）。现在 `NSEvent.pressedMouseButtons != 0` 时
**推迟一秒再写**，绝不插在手上的操作中间。

### 实测：这些操作到底慢不慢（v1.3.30）

光看代码猜不出来，所以搭了个跑**真实界面**（真 `ContentView` + 真窗口 + 真渲染）
的探针，装 `CFRunLoopObserver` 逐项量：

| 操作 | 耗时 |
|------|------|
| `moveTOCEntry` 一次 | 0.1 ms |
| 连续 `moveTOCEntry` ×10（模拟拖动） | 0.3 ms |
| `goToTOCEntry`（点击目录跳转） | 0.1 ~ 0.7 ms |
| 切「只读 → 编辑」 | 0.1 ms |
| `pdfView.currentPage` / `scaleFactor` / `document.index(for:)` | 0.00 ms/次 |
| 慢轮次汇总 | **只有「打开文档」204 ms 一轮** |

> ⚠️ **测量方法本身有个坑**：一开始用"两次 `beforeWaiting` 的间隔"当耗时，
> 结果每轮都显示 ~300 ms，看着像"每轮都卡 300 ms" —— 其实那是 `syncState()`
> 的 0.3 秒 Timer 带来的**空闲等待**。要量 `afterWaiting → beforeWaiting`
> （这一轮真正处理掉的活）才对。
>
> 另外：**别用"文件大小"判断有没有写盘** —— 改名"改名"→"再改"字节数恰好相同。

① 注入 bridge ✅　③ 改目录后 hasUnsavedChanges = true ✅
applicationShouldTerminate 被调用 ✅ → 拿到 viewModel ✅ → 会弹确认框 ✅

### 关闭时怎么问

- **关标签 / 关闭全部标签** → `AppViewModel.closeTab` 先调 `confirmClose()`
- **⌘Q / 关闭窗口** → `AppDelegate.applicationShouldTerminate` 逐个标签确认；
  任何一个"取消"或"保存失败"都返回 `.terminateCancel`

为什么用 `NSAlert` 而不是 SwiftUI 的 sheet：`applicationShouldTerminate` 是 AppKit 的
**同步**出口，没法在那里等一个异步弹窗。

> ### ⚠️ `NSApp.delegate as? AppDelegate` **永远拿不到**（v1.3.29 修的）
>
> 第一版是让 `ContentView.onAppear` 把 viewModel 塞给
> `(NSApp.delegate as? AppDelegate)` —— 结果**关闭时永远不提示**。
>
> 实测（`/tmp/appdelegateprobe`，跑一个真的 `@main App`）：
>
> ```
> NSApp.delegate 的实际类型: AppDelegate     ← SwiftUI 内部自己的，名字也叫这个
> 是 ProbeDelegate 吗: false
> 能 as? 成 ProbeDelegate 吗: ❌ 不行（nil）
> @NSApplicationDelegateAdaptor 确实实例化了我们的类: ✅
> ```
>
> SwiftUI 的 `@NSApplicationDelegateAdaptor` 会**包一层**，`NSApp.delegate` 是它自己那个
> （类型名恰好也叫 `AppDelegate`），转换必然失败。所以改成显式的全局注册表
> `AppModelBridge.appViewModel`，由 `ContentView` 注入。
>
> 顺带一个推论：**你那个 delegate 实例确实会被创建** —— 所以"在它的 `init` 里注册到某个
> 全局"也是可行的（本项目用的是注册表那一版，更显式）。

> ⚠️ 点红叉关窗口那条路，`applicationShouldTerminate` 返回取消时窗口**已经关掉了** ——
> 所以额外实现了 `applicationShouldHandleReopen`，点一下 Dock 图标就能把窗口找回来，
> 不至于留下"app 还活着但没窗口"的死角。
>
> **保存失败时不会关闭文档** —— 否则用户以为已经保存好，实际改动没了。

### 写入本身：先写临时文件，自检通过再原子替换

`PDFDocument.write(to:)` 是**直接覆盖原文件的**：一旦中途失败（磁盘满、进程被杀），
原文件已经被截断，用户的东西就没了。

所以现在写盘一律绕一圈：

1. 写到**同目录下的隐藏临时文件**（`.名字.tmp-<UUID>.pdf`，前导点 = 访达里看不见）
2. 注入目录（PDFKit 不写目录，见上文）
3. **自检**：用 `PDFDocument(url:)` 重新打开，要求页数一致、目录能原样读回
4. `FileManager.replaceItemAt` **原子替换**原文件

中间任何一步失败都**不碰原文件**。有了这层保证，自动保存才敢不生成备份 ——
用户明确说过不要每次编辑都堆一份备份。

> 实测（`/tmp/autosaveprobe`，21/21 通过）：替换之后**原来那个 `PDFDocument` 实例仍完全正常**
> —— `documentURL` 没变、能继续读页/读批注、能再 `write` 回同一路径，第二次写出的内容也对。
> 所以不需要在替换后重新加载文档。
>
> 另有一条兜底路径：沙箱里同目录**写不了新文件**时（`user-selected.read-write` 给的是"那个文件"、
> 不一定覆盖它所在的目录），退回直接写原文件 —— 没有上面那层保护，但功能可用。

### 备份的去向与开关

**默认就放在原文件旁边**（v1.3.12 改的）：

```
和原文件同一个文件夹/
    测试文件-备份-20261009-174236.pdf
```

> 早先只放应用数据目录，那个路径在沙箱里是
> `~/Library/Containers/com.jiejie.pdfreader/Data/Library/Application Support/PDFReader/Backups/`，
> **又深、又带容器前缀**，用户按弹窗给的文字路径去 Finder 里根本找不到
> （实测用户反馈"保存的备份并不存在"，其实文件就在那儿）。

现在多了两个偏好（「设置」⌘, 里改）：

- **手动保存时创建备份**（默认开）—— 关掉之后 ⌘S 也只写文件、不产生副本；
- **备份位置**：`原文件旁边`（默认）或**指定目录**（自己选一个文件夹）。
  自定义目录用 **security-scoped bookmark** 持久化 —— 沙箱下用户选的目录，
  退出进程授权就没了，光存路径字符串下次启动读不到（`app-scope` 权限已在 entitlements 里）。
  写不进去时**抛错并由调用方回退**到默认落点，同时把这件事显示在设置里，
  而不是悄悄换个地方放（"我明明选了目录、文件却跑到别处"最难排查）。

同一文件最多保留 20 份历史备份，超出后按时间从最旧的开始清理。
清理**只认我们自己生成的备份名**（`<名>-备份-<时间戳>`，以及 v1.3.12 之前的 `<名>-<时间戳>`）——
备份目录现在**可能是用户自己的文件夹**，绝不能误删别人的文件（实测：同目录里的
`重要资料.pdf`、`测试文件-abc.pdf` 连存 25 次后都还在）。

同一秒内多次保存会在时间戳后加 `-2`、`-3`…，不会互相覆盖。

还原方式：把备份文件复制回原路径覆盖即可。

### 总开关：Release 默认关，要用自己在设置里打开（v1.3.68）

**Release 构建默认不记日志**（效率优先），Debug 构建默认记。
入口：设置（⌘,）→「诊断」→「记录诊断日志」，**改完立即生效，不用重启**。

关掉之后这些统统不做 —— 全都是"平时一直在花时间"的东西：

| 关掉的 | 原来在花什么 |
|---|---|
| 日志文件 | 连目录都不建、句柄都不开 —— 一个文件都不出现 |
| 主线程看门狗 | 那个 `CFRunLoopObserver` **每一轮 runloop 都会被调一次** |
| 卡死检测线程 | 后台每秒醒一次 |
| 鼠标事件监听 | 每次点击都要过一遍回调 |
| `record` / `measure` / `count` / `activity` | 直接 return，连一次 `write(2)` 都不发 |

`record(_:)` 的参数是 **`@autoclosure`**（惰性）—— 关着的时候**连那句话都不拼**，
所有调用点自动省掉。这不是理论收益：`PDFViewModel.markDirty()` 里那句
`record("标脏 ← …" + Thread.callStackSymbols…)` 会**走一遍调用栈并符号化**
（几十微秒到毫秒级），而它在**每一次文档改动**时都调 —— 以前作为实参先算好再传进去，
关不关诊断都照算不误。`startSession(version:)` 同理（它的参数要去 stat 可执行文件取构建时刻）。

⚠️ **唯一的例外：崩溃兜底永远装着**（信号 handler + `NSSetUncaughtExceptionHandler`）。
它平时**零开销** —— 只在进程要死的那一刻才动一下，而它是"用户报崩溃"时**唯一的证据来源**；
关掉它，问题就永远查不出来了（下面那次"一滚就死"就是靠它定位的）。
诊断关着时它退到 `stderr`（Console.app 里能看到），**不落文件** —— 保持"关着就一个文件都不建"。

⚠️ **跑自动化验证时会强制打开**：`AutomationHooks` 那套钩子**全靠回读日志判结果**
（"滚了 600 步还活着""关窗口时问了没有"），而自检恰恰是用命令行
`swift build -c release` 出的包跑的 —— 那正是默认关的那一种。判据：
进程环境里存在任一 `PDFREADER_*` 变量，或命令行带 `--autoquit-after`。

| 记录内容 | 用来回答什么问题 |
|---------|-----------------|
| 每次启动的版本号与时间 | 跑的是哪一版 |
| **主线程慢轮次**（>120ms）+ 当时的操作标签 | 卡了多久、卡在哪一步 |
| 拖放回调次数（起手 / 跨行 / 更新 / 放下） | 拖拽会话有没有被异常频繁触发 |
| 关闭文档的**每一步判定**（有没有未保存改动、偏好开没开、弹窗选了什么） | "为什么不提示保存" |
| `applicationShouldTerminate` 有没有被调用 | 关闭流程有没有被走到 |
| **崩溃遗言**（异常名 + 原因 + 调用栈，v1.3.52 / 信号栈 v1.3.53） | 崩在哪、什么异常 —— 哪怕不在 Xcode 里跑也能看到 |
| **主线程卡死**（后台线程盯着，v1.3.53） | 卡了多久才回来、卡住的瞬间在干什么 |

### 崩溃会留下遗言（v1.3.52 → v1.3.53 做成两路）

诊断日志原来是**异步写盘**的 —— 进程崩掉时，队列里还没落盘的那几条一起丢。
用户报的那次崩溃，日志就是**断在一半**（最后停在 `慢轮次 2689 ms`，崩在哪一句都看不到）。

现在两路兜底，**谁也替不了谁**：

| 哪一路 | 管什么 | 典型现场 |
|---|---|---|
| `NSSetUncaughtExceptionHandler` | **ObjC 异常**（`unrecognized selector` / KVC） | v1.3.51 修的那两次崩溃 |
| **信号 handler**（`SIGABRT/SIGSEGV/SIGBUS/SIGILL/SIGTRAP`） | 一切走到信号层的死法 | v1.3.53 这次：Metal 校验层直接 `abort()` |

为什么信号那路必须有：ObjC 异常**一路没人接**时，最后是被 C++ 的 `std::terminate` 收掉的
（`__cxa_throw → std::__terminate → abort`）—— 这条路**不经过** uncaught handler。
信号 handler 里只用 `write` / `strlcat` / `backtrace_symbols_fd`（全是 async-signal-safe 的），
写一句"收到什么信号 + 当时的操作 + 当前线程调用栈"，然后把信号交回默认处理
（该死还是死，系统崩溃报告照旧生成）。

```
‼️ 进程收到致命信号 SIGABRT（abort：未捕获异常 / 断言失败）
   最近活动：页码变了 → 刷新界面
0   PDFReader     …installCrashSignalHandlers…
4   libsystem_c   abort
…
```

另两点限制照旧：**在 Xcode 里跑时未必轮得到它**（调试器会先停在异常处，用户点了继续才走到这里，
所以 Xcode 里还是以调试器的栈为准）；符号是 mangled 的，要具体名字用 `atos` 或 Xcode 解。

### 「合集2.3.pdf 一滚就死」的真凶：Xcode 的 Metal API Validation（v1.3.53，已定位并根治）

杰哥第二次报同一个文件：**不管怎么打开，滚动一下就死**。命令行 Release 版滚 500 步
反复测都好好的 —— 差别在**运行方式**：他是在 Xcode 里 ⌘R 跑的，而 Xcode 的
Run → Diagnostics → **Metal API Validation 默认开着**。

先补上"能留下证据"的能力，再复现。崩溃现场（信号兜底写进他自己那份日志里）：

```
‼️ 进程收到致命信号 SIGABRT（abort：未捕获异常 / 断言失败）
   最近活动：页码变了 → 刷新界面
abort
MTLReportFailure
_MTLMessageContextEndNewNSErrorOrAbort
-[MTLDebugRenderCommandEncoder validateCommonDrawErrors:…]
-[MTLDebugRenderCommandEncoder drawPrimitives:…]
CA::OGL::MetalContext::draw
CA::OGL::MetalContext::stroke_lines          ← PDF 页面里的矢量线条
CA::CG::WideLineRenderer::flush
```

**PDFKit 画页面线条 → CoreAnimation 走 Metal → 校验层判定这次 draw call 有问题 → 直接 `abort()`。**
跟本项目代码无关（一行 Metal 都没有），是"给写 Metal 的人用的调试层"在 PDFKit 内部实现上误报。

对照实验（**同一份二进制**，只差一个环境变量，都是沙盒 Debug 构建、投 600 步真实滚轮事件）：

| 运行条件 | 结果 |
|---|---|
| `MTL_DEBUG_LAYER=1`（Xcode 默认） | **13.9 秒后 SIGABRT** |
| 不设 | 滚完 600 步，进程好好的 |
| `MTL_DEBUG_LAYER=1` + 下面的修复 | 滚完 600 步，进程好好的 ✅ |

**修法两层**：

1. **app 自己摘掉**（`DebugMetalValidation.neutralize()`，放在 `App.init()` 里）——
   时机必须极早：Metal 是在**创建 MTLDevice 那一刻**读这个变量的（CoreAnimation 首次渲染），
   晚一步就没用，而 `App.init()` 比 `NSApplicationMain` 还早。这样**不管谁启动**都不会中招；
2. **scheme 里显式关掉**（`PDFReader.xcscheme` 的 `LaunchAction` 注入 `MTL_DEBUG_LAYER=0`）——
   双保险，也省掉校验层的开销。项目不用 Metal，关掉零损失。

> 复现这件事本身也有坑，都在 `AutomationHooks` 里记着：命令行**不能**用
> `window.sendEvent` 之外的投递方式（`NSApp.postEvent` 出来的事件 `window` 是 nil，
> 投 400 步页面一动不动），而 `NSEvent(cgEvent:)` **不做窗口坐标转换**，
> 得自己把 y 反向翻一次，否则命中测试落在视图外。

**实现要点**：用 `CFRunLoopObserver` 量 `afterWaiting → beforeWaiting` 之间的时间
（**不含空闲等待** —— 早期用"两次 `beforeWaiting` 的间隔"，把 Timer 的空闲等待也算成
"卡了 300ms"，误导过一整轮排查）。

> ⚠️ **看门狗原来在主线程上，最需要它的时候它自己不动**（v1.3.53 修的）：
> 用户那份"滚动就死"的日志里，打开文件之后**一个字都没有** —— 因为所有记录都发生在主线程，
> 而主线程正是卡住的那一个。现在另起了一条**后台线程**盯着「主线程还活着吗」：
> 每秒看一眼，卡够 5 秒就写一条（`⛔️ 主线程卡死：已 N 秒没有进展…`），恢复时再写一条
> `✅ 主线程恢复`。判据是"`afterWaiting` 之后迟迟没有 `beforeWaiting`"，
> **不是**"主线程没动静" —— 后者会把"开着窗口没人操作"也报成卡死（自检当场抓到过）。
>
> **日志改成了同步 `write(2)` 直写**：原来异步写盘，进程被强杀（用户卡急了 ⌘⌥Esc）
> 时队列里的内容一起丢。

### 日志上线当天就抓到的两个真问题（v1.3.32）

**① 关闭时永远不提示保存** —— `AppModelBridge.appViewModel` 原来是 **weak** 引用：

```
[16:40:35.751] applicationShouldTerminateAfterLastWindowClosed 被调用 → true
[16:40:35.773] ⚠️ applicationShouldTerminate：bridge 里没有 viewModel → 直接放行（不会提示）
```

点窗口红叉时，SwiftUI **先销毁窗口的视图树**（`ContentView` 连同它的 `@StateObject` 一起没了），
**22 毫秒后**才调 `applicationShouldTerminate` —— 那一刻 weak 引用**已经是 nil**，
所以"有没有未保存的改动"根本问不出去。

→ 改成**强引用**（不会造成循环：`AppViewModel` 不反向持有它）。
修完再跑同一条路径：`applicationShouldTerminate 被调用 · tabs=0 → 全部通过，允许退出` ✅

**② 就算提示了，选「保存」也会失败** —— `PDFViewModel.pdfView` 同样是 weak，
视图销毁后 `saveAnnotationsToDisk` 拿不到 document。
→ 新增 `boundDocument`（`bind` 时记下的强引用）+ `currentDocument` 兜底；
保存路径改用后者。不修的话会出现"关不掉文档、还留下一个没窗口的 app"。

> 这两条都**只在"点红叉关窗口"这条路上出现** —— 按 ⌘Q 时窗口还没销毁，
> 所以在此之前用 ⌘Q 测是测不出来的。

### 测"关闭提示"的正确方式

**用 ⌘Q 或点窗口红叉，不要在 Xcode 里按 ⌘R 重启来测。**

⌘R 会**直接杀掉**上一个进程，`applicationShouldTerminate` 根本不会被调用，自然也没有提示。
（探针确认过：`@NSApplicationDelegateAdaptor` 的转发是正常的 ——
自己调 `NSApp.terminate(nil)` 时 `applicationShouldTerminate` 会被调到。）

> 顺带一条坑：`NSApp.delegate` **不是**你提供的那个 delegate。SwiftUI 会包一层，
> 而它内部那个类的**类型名也叫 `AppDelegate`** —— 所以 `NSApp.delegate as? AppDelegate`
> 永远返回 nil（实测 `is` 判断为 false）。要拿自己的 delegate 得用显式注册表
> （本项目的 `AppModelBridge`）。

## 关闭确认：先弹框，再关窗口（v1.3.33）

之前"有没有未保存的改动"问在 `applicationShouldTerminate` 里 —— **那个出口太晚了**：

```
[16:57:15.951] applicationShouldTerminateAfterLastWindowClosed 被调用 → true
[16:57:15.953] applicationShouldTerminate 被调用 · tabs=1     ← 2 毫秒之后，窗口已经没了
```

点红叉时 SwiftUI **先销毁窗口与视图树**，AppKit 才来问"最后一个窗口关了，要不要退出"。
于是用户看到的是「**文件已经关了，才弹提示框**」；而这时窗口已经没了，用户点「取消」
既留不住窗口，还会**再触发一次** terminate 把框弹回来（日志里连弹三发），
唯一出路是选「保存 / 不保存」。

**现在**：确认挪到 `NSWindowDelegate.windowShouldClose(_:)` —— 那是**窗口真正关闭之前**
的同步出口，返回 `false` 窗口就留着。

| 操作 | 走哪条路 |
|------|---------|
| 点窗口红叉 / ⌘W / 点标签上的叉 | `WindowCloseGuard.windowShouldClose`（**窗口还没关，先问**） |
| ⌘Q / 退出应用 | `AppDelegate.applicationShouldTerminate`（窗口还在，时机本来就对） |

SwiftUI 自己管着窗口的 delegate，所以 `Utils/WindowCloseGuard.swift` 做了一层**代理**：
换掉 `window.delegate`，只实现 `windowShouldClose`，**其余消息原样转发**回去
（`responds(to:)` + `forwardingTarget(for:)`），SwiftUI 的状态恢复、窗口动画、
`windowWillClose` 收尾都不受影响。

两个实测记住的坑：

- **`NSWindow.close()` 不经过 `windowShouldClose`** —— 它"无视 delegate 是否同意"直接关窗。
  自动化验证必须用 `performClose(nil)`（等价于点了一下红叉）。
  这一点之前一直踩空：用 `close()` 跑出来的日志会让人误以为"拦截没生效"。
- `NSWindow.delegate` 是 **weak**：装上去不自己强引用，下一行就没了。

`confirmClose()` 里用户选「不保存」时会**把脏标记清掉** —— 不然窗口关掉之后那一发
`applicationShouldTerminate` 会再问一遍、把框弹第二次。

> 实测（真 app）：无改动时正常退出；有改动时日志停在
> `confirmClose：准备弹窗` 而**没有** `applicationShouldTerminateAfterLastWindowClosed`，
> 也就是**窗口确实还开着**。配套探针 `/tmp/closeguardprobe` 10/10：
> 返回 `false` 窗口仍可见、返回 `true` 真的关掉且 `windowWillClose` 转发到位。

## 目录拖拽：为什么"第二次拖不动、拖完点不动"（v1.3.33）

日志抓到的现场：

```
[16:54:51.781] performDrop：找不到被拖的行 → 当作没处理
[16:54:51.788]   计数（卡顿前累计）：拖放.onDrag 起手=1  拖放.performDrop=1
```

`onDrag` 明明起手了，`performDrop` 却拿不到"被拖的是谁"，而且**返回了 false**。
这个返回值在 AppKit 那层不是"我有没有移动数据"，而是**"这次拖拽有没有人接手"** ——
返回 false 意味着"没人接受"，拖拽会话**悬在那里不走**，随后几秒里鼠标的点击和拖动
**全都失去响应**：正是「刚刚拖动完点了也没反应、还得等几秒」。

载荷（`dragState.id`）被提前清掉有三个来源，两处是坑，都已收紧：

1. **松手后的看门狗**每 0.12 秒查一次 `NSEvent.pressedMouseButtons`，而 `performDrop`
   要等 AppKit 收尾 + SwiftUI 下一帧（实测差 100ms 以上）—— 立刻清就把本次 drop 的载荷抹了。
   → 改成**延迟 1.5 秒清**，清之前核对写入时间戳（时间戳变了＝新的一次拖动，别动）。
2. **父级 `List` 上的兜底 `onDrop`**：拖到某一行时父子回调先后没有保证，父级先跑就清了载荷。
   → 兜底只清落点提示，**绝不碰载荷**。
3. **`validateDrop` 拿载荷做判断**（`dragState.id != row.id`）：载荷一残留，
   那一行的所有落点（前/后/里面）都被静默拒绝 —— "这一行怎么拖都没反应"。
   → 只校验载荷类型；"拖到自己/子孙"由 `moveTOCEntry` 的环检测挡。

对应三处改动：`performDrop` **无条件返回 true**、看门狗延迟清理、`validateDrop` 不再依赖载荷。

### 目录删不掉：两层原因（v1.3.34）

症状：**删掉顶层目录，里面的子目录又冒出来，顶层目录删不掉**。查下来是两层叠在一起。

**内存层**：`removeTOCEntry` 里有这么一段

```swift
if root.numberOfChildren == 0 { document.outlineRoot = nil }   // ← 罪魁
```

本意是"删空了把根也收掉"。但实测（`/tmp/tocdeleteprobe`）：把 `outlineRoot` 设成
nil 之后，PDFKit **会重新从文件里解析 `/Outlines`** —— 而我们的目录正是被
`PDFOutlineWriter` 注入到**文件**里的，于是刚删掉的整棵树又回来了。
这份文件只有一个顶层项，删它就必然删空 → 必然触发。

**文件层**：`writeDocument` 里

```swift
if !items.isEmpty { try PDFOutlineWriter.inject(items, ...) }   // ← 空目录时整段跳过
```

**注入器本来就支持空目录**（`removingOutlines` 会把 catalog 里的 `/Outlines` 键删掉），
但调用方在空目录时跳过了它。而实测确认 **PDFKit 的 `write` 会保留文件里原有的
`/Outlines`** —— 所以不主动删，删除就永远进不了文件。

→ 两处都改掉，并给写盘自检加了**反向检查**（空目录时要求文件里找不到目录）。

验证用两条独立路径，都对上才算数：

| 路径 | 修复前 | 修复后 |
|------|--------|--------|
| PDFKit 重新打开写出的文件 | 顶层 1 项 | **顶层 0 项** ✅ |
| 字节级解析 catalog（`/tmp/pdfcatcheck.py`） | 有 `/Outlines`（→6210） | **没有** ✅ |

### 拖拽"慢/点不动"怎么查（v1.3.34）

日志补了一层能**一句话定性**的记录。拖放刚结束时，监听会记下每一次鼠标按下/抬起，
并带上"距上次放下多少毫秒"（只在放下后 6 秒内记，其余静默）：

| 日志里看到 | 说明 |
|-----------|------|
| 有「鼠标按下」+ 有「点击目录项」 | 事件到了、也被处理了 |
| 有「鼠标按下」+ **没有**「点击目录项」 | 到了视图这一层却没被接住 |
| **连「鼠标按下」都没有** | 在 AppKit 那层就被吞了（拖拽会话没收干净） |

同时 `reloadTOC` / 目录跳转 / 保存写盘都套上了 `measure`，超过阈值会记一条带毫秒的
记录；`performDrop` 后半秒还会 flush 一次「目录行 body 求值」计数，回答"拖一下到底
重建了多少行"。

### 拖拽源：为什么不用 SwiftUI 的 `.onDrag`（v1.3.35）

上面那张表用一次实跑就给出了答案 —— 是**第三种情况再往前一步**：

```
[17:29:58.584] performDrop：成功
[17:29:59.923] 鼠标按下 · 距上次放下 1338 ms
[17:30:00.412] 鼠标按下 · 1827 ms     ← 又按（上一次的"抬起"根本没来）
[17:30:00.851] 鼠标按下 · 2266 ms
[17:30:01.467] 鼠标按下 · 2883 ms
[17:30:01.563] 鼠标抬起 · 2979 ms     ← 隔了近 3 秒才收到"抬起"
```

**4 次"按下"只有 1 次"抬起"**，而且这几次点击**都没有** `拖放.onDrag 起手` ——
拖拽会话根本没建起来，鼠标却被拖拽机制**扣住**了。另外日志里**一条慢轮次都没有**：
主线程被同步的鼠标跟踪占着，runloop 观察器压根跑不到，所以它**不像卡顿**。
（同一份日志还给出反证：`目录行 body 求值=12`，重建只有 12 次 —— "重建太贵"可以排除。）

结论：**SwiftUI 的 `.onDrag` 在 drop 之后会进入一个"夹生"状态**，把鼠标扣住一两秒
（"点几下能提前恢复"＝每次点击都在喂它的状态机）。所以拖拽源改成自己用 AppKit 控制：
`TOCDragHandleView`（`NSView` + `NSDraggingSource`）—— `mouseDown` 不做任何跟踪、
`mouseDragged` 超 3pt 才 `beginDraggingSession`、会话结束由
`draggingSession(_:endedAt:operation:)` **明确回调**。载荷用 `NSPasteboardItem` 写
`.string`（类型标识就是 `public.utf8-plain-text`，和 `.onDrop(of: [.utf8PlainText])`
完全一致），所以 **`TOCDropDelegate` 一个字都没改**。

配套三处：`performDrop` 的数据变更**延后到下一轮主队列**（先让系统做完拖拽收尾）、
去掉拖拽热区上的 `.help`（tooltip 计时窗和症状时间窗重合）、`dropHint` 只在非 nil 时写。

> 编译坑：Swift 里 `NSItemProvider` **没有**暴露 `NSPasteboardWriting` conformance
> （ObjC 头文件里有），`NSDraggingItem(pasteboardWriter: provider)` 会报
> `does not conform`。改用 `NSPasteboardItem`。

> ✅ **实跑确认**：`.onDrop` 接住了 AppKit 发起的拖拽 —— 日志里
> `拖拽会话结束：operation=16（已被接受）`，两次拖动之间只剩 0.4~1.4 秒（人的操作时间）。

### 拖到列表下方空白 = 移到最后（v1.3.36）

`List` 会占满剩余高度，目录项少的时候下面留着一大片空白 —— 而"把某一项移到最后"
最自然的动作就是往那片空白拖。没有目标接受它的时候，日志里就是：

```
拖放.onDrag 起手：「2. 规格」
拖拽会话结束：operation=0（没有任何目标接受）      ← 拖了，没人接
```

所以 `List` 上恢复了一个 `.onDrop` 兜底，落点为空则
`moveTOCEntry(row, relativeTo: nil, as: .after)`（追加到顶层末尾）。

> 为什么父子两层都当拖拽目标不会打架：**AppKit 的拖拽只会发给最深的接受者** ——
> 鼠标在某一行上就只调那一行的 delegate，落在空白处才轮到 `List`。

### 图标按钮"点了没反应"：命中区只剩笔画（v1.3.36）

SwiftUI 的 `Button` 命中区默认只认 label 里**不透明**的内容。所以：

```swift
Image(systemName: "line.diagonal.arrow")
    .frame(width: 26, height: 22)
    .background(RoundedRectangle(cornerRadius: 5)
        .fill(isActive ? Color.accentColor : Color.clear))    // ← 未激活＝全透明
```

未激活时底色全透明 → **命中区只剩那根斜线的笔画**（14pt 下只有一两个点宽）；
`.frame` 只撑开布局、**不扩大命中区**；激活之后底色变不透明 → 命中区突然覆盖整块，
所以"再点一次就中了"，看起来特别随机。

修法是在 label 末尾加 `.contentShape(Rectangle())`。同类问题一次补了四处：
标注工具条、目录面板那排按钮（`Label + frame(maxWidth:.infinity)` 撑出的空白不可点）、
标签页关闭按钮（13×13 的细线 `xmark`）、搜索结果翻页按钮（`chevron.up/down`）；
折叠小三角另外从 14×14 撑到 20×20。

## 切换标签：位置、缩放、脏标记都得留住（v1.3.38）

切标签时 SwiftUI 会**复用**同一个 `PDFView`，走的是 `updateNSView` → `bind()`。
而 `bind()` 里有几句本来是"新文档专用"的代码，在切标签时会造成两个症状：

| 代码 | 后果 |
|------|------|
| `unsavedChanges.clear()` | 脏标记被抹掉 → **编辑的没保存，关闭也不提示** |
| `restoreProgress()` | 拿 `BookmarksStore` 里**上次关闭该文件时**的位置覆盖当前视图 → **位置和缩放全变了** |

修法：**把"新打开的文档"和"切标签回来的文档"分开**。

- `bind()` 里用 `ObjectIdentifier(document)` 判断是不是换了文档，
  只有真换了才清撤销历史 / 重置钉住的缩放；**脏标记不清**（新标签的 viewModel
  本来就是新建的，初始就是干净的）。
- 切走时把视图状态（页号 + 页内比例 + 缩放）**记进内存**（`pendingViewState`）——
  `updateNSView` 里换 document **之前**、以及 `dismantleNSView` 里各存一次
  （切标签时 PDFView 有时复用、有时销毁，两条路都得管）。
- 切回来用**内存那份**恢复；只有新文档才去读 `BookmarksStore`。

> 实测：标签 1 设成 页 1 / 缩放 0.8 → 切走 → 切回 → `页=1 缩放=0.800 未保存=true`，
> 而不是存储里那份 `页 2 / 缩放 1.6`。

### 标签栏**默认就显示**（v1.3.45）

macOS 只在 `NSWindow.userTabbingPreference == .always` 时才让**单独一个窗口**
也显示标签栏。本机实测是 `2（inFullScreen）`（「系统设置 → 桌面与程序坞 →
优先以标签页方式打开文稿」选了"全屏时"），所以默认**看不到标签栏** ——
要开第二个文件才冒出来、关到只剩一个又缩回去。

探针 `tools/probes/tabmodeeprobe.swift` 的实测（真窗口）：

```
上屏之后设 tabbingMode = .preferred   → 标签栏**不会**自己冒出来
  （头文件写明它 "should be set before a window is shown"，
    而窗口是 SwiftUI 建的，只能在它上屏之后才拿得到 —— 这条做不到）
再调 toggleTabBar(_:)                 → 标签栏出现 ✅
关到只剩一个标签                       → 标签栏仍然显示 ✅
```

所以 `DocumentWindows.showTabBarAndMerge` 做三件事，**顺序不能反**：

```swift
window.tabbingMode = .preferred
if (window.tabbedWindows?.count ?? 0) > 1 { return }   // 已在别人的组里
if let sibling = …同 identifier 的别的窗口… {
    insert(window, intoGroupOf: sibling)               // ① 先并组
    return
}
showTabBarOnce(for: window)                            // ② 它是第一个 → 再开标签栏
```

反过来的话第二个窗口会先给自己开一条标签栏（自成一组），之后就跟第一个窗口
**并不到一起**了。

`showTabBarOnce` 两条讲究：

- **先查 `isTabBarVisible` 再调** —— `toggleTabBar` 是**开关**，不看状态就调会把
  已经显示的关掉；
- **每个窗口只开一次**（`Set<ObjectIdentifier>` 记着）—— 用户手动隐藏标签栏后，
  切走再切回来不该又给它打开（那会变成"关不掉"）。窗口关掉时 `forget` 掉记录。

### ⚠️ 三个必须自己补的地方（都有实测支撑）

**① 不会自动合并。** `tabbingIdentifier` 一样、`tabbingMode` 也是 `automatic`，
macOS **还是不会自己并**（探针实测；`AppleWindowTabbingMode` 这个键在本机压根不存在）。
必须显式并组。

**并组的位置按「文件的打开顺序」排，不能按"谁先准备好"排**：

- `prepareWhenReady` 要等各自的 `isVisible`，各窗口等的轮数不同；
- 窗口**谁先上屏**本身就是并行的、不保证（试过按"窗口登记顺序"排，一样会错）。

唯一有序的是 `open(_:)` 收到的那个 `urls` 数组 —— 在那里给每个文件记一个递增的
**打开序号**（`DocumentOpener.requestedOrder`），并组时用
`NSWindowTabGroup.insertWindow(_:atIndex:)` 插到第一个"序号比我大"的窗口前面。
连跑 4 次，顺序稳定是 `测试文件 | tabB | tabC`。

退路（拿不到 `tabGroup` 时）才用 `addTabbedWindow(_:ordered:)`，注意两处反直觉：
`ordered: .above` 才是"往后排"（`.below` 会插到前面，顺序整个倒过来）；
落脚点要选**这一组里最后一个标签**，否则顺序会乱。

**② 后台标签永远不会"成为 key"。** 所以原来靠 `didBecomeKey` 通知装的关闭确认代理
**装不上** —— 用户点标签上的叉时 `windowShouldClose` 不调用，**有未保存改动也不提示**。
现在窗口一被登记成文档窗口就把代理装上（`DocumentWindows.prepareWhenReady`）。

**③ SwiftUI 的窗口类没有 `newWindowForTab:`**（系统标签栏那个 `+` 发的就是它）。
直接调用会崩：`-[SwiftUI.AppKitWindow newWindowForTab:]: unrecognized selector`。
在窗口 delegate 和 AppDelegate 上各实现了一份来补这个空。

### 标签上显示什么

`DocumentTab.displayName` = 文件名**不带扩展名** → 直接当窗口标题用，
也就是系统标签栏上那个字。鼠标悬停仍能看到所在文件夹（`titleTooltip`）。

### 跨窗口的那份"桥"改成按窗口登记

`AppModelBridge` 不再是全应用一份 viewModel，改成
`register(_:for:)` / `unregister(_:)` / `viewModel(for:)`。
仍然是**强引用**（理由没变：SwiftUI 先销毁视图树、AppKit 之后才来问"要不要保存"），
窗口真关掉时在 `windowWillClose` 里注销 —— 实现了 `windowWillClose` 就等于
**接下了**这条消息，`forwardingTarget` 不会再转发，必须手动交回原 delegate。

### ⚠️ 拖出去的标签会被吸回来、还原的最小化窗口会被并（v1.3.71）

杰哥报的两个问题，**成因是同一个**：

> 「打开了多个文件，不能通过拖拽标签页独立出一个新的窗口。」
> 「app 最小化的时候再打开其他文件，看起来是个新独立窗口，
>  但把最小化的那个窗口点开，就自动合并成一个窗口了。」

都在 `DocumentWindows.showTabBarAndMerge` 里 —— 它设计成"每见到一个文档窗口就
找同伴并组"，而 `prepareWhenReady` 会被**每一次"成为 key"**再调一遍：

| 现场 | 那一刻的状态 | 后果 |
|---|---|---|
| 用户把标签**拖出去** | `tabbedWindows` 只剩它自己（**不是** `> 1`，那道防重复的判断接不住） | 我们**亲手**把用户刚拖出来的标签并了回去 → "拖不出来" |
| 用户点 Dock **还原**最小化的窗口 | 最小化期间 `isVisible == false`，所以那个文件老实另立了一组（用户看到的就是"新独立窗口"）；还原时它重新成为 key | 它被并进**新窗口**那一组 → "点开就合并成一个了" |

修法只有一条判据：**一个窗口的"入境手续"只办一次**（`preparedWindows`），
而且必须放在 `showTabBarAndMerge` 的**最前面** —— 每条分支都要算"办过了"，
放中间会漏掉"并进组就 return"那条路上的窗口。

> ⚠️ 第一版判断是错的：以为"最小化的窗口被当成了落脚点"。
> 探针实测 —— **最小化之后 `isVisible` 就是 `false`**，这条路径根本不存在。
> 真正出问题的是**还原的那一下**。

**实测（两层证据）**

1. `tools/probes/tabdetachprobe.swift`：旧逻辑 vs 新逻辑并排跑真窗口，**13/13**；
2. 真 app 端到端（`PDFREADER_AUTOTEST_TABFLOW=<a.pdf>,<b.pdf>`），
   并且**先 `git stash` 掉修复做对照组**：

```
── 旧代码 ──
还原 A 并让它成为 key ……
窗口分页：「tabtest_a」插到第 1 位（现在 2 个标签：tabtest_a | tabtest_b）   ← 合了 ❌
还原 A 之后：窗口[0] 同组标签数=2 · 窗口[1] 同组标签数=2

── 新代码 ──
还原 A 并让它成为 key ……
（一条「窗口分页」记录都没有）
还原 A 之后：窗口[0] 同组标签数=1 · 窗口[1] 同组标签数=1                   ← 各站各的 ✅
```

> ⚠️ 写这条自动化时踩的坑：**从终端裸跑的 app 拿不到键盘焦点** ——
> `deminiaturize` / `makeKeyAndOrderFront` 之后 `didBecomeKey` **一次都不发**，
> 而产品的并组正挂在那个通知上（`windowDidBecomeKeyOrMain`）。
> 不手动把"成为 key"那个回调干的事做一遍，跑出来的日志会让人误以为
> "本来就不会合并"（第一版对照组就是这么被骗过去的）。
> 钩子里现在显式补了 `WindowCloseGuardInstaller.install` + `DocumentWindows.prepareWhenReady`。

**顺带验到的一条边界事实**：`tabbingMode = .preferred` 如果在窗口**上屏之前**设，
系统**自己就会**把同 identifier 的新窗口并进来（`tabbingMode` 头文件那句
"This should be set **before a window is shown**"的另一面）。产品代码只能在上屏
**之后**设（窗口是 SwiftUI 建的）—— 也正因如此，系统不帮忙并、我们才必须手动
`addTabbedWindow`；反过来说，也就不会把用户主动拖出去的窗口吸回去。

## 多窗口改造的两个后遗症（v1.3.41）

### 一、单例里存一个 `NSView` = 谁最后打开谁独占

`SpaceDragPanMonitor`（空格 + 拖动平移）和 `ScrollZoomMonitor`（⌥ + 滚轮缩放）
原来都是 `static let shared`，里面只有一个 `weak var pdfView`，`attach` 还先 `detach()`。
一个窗口装所有文件时全局确实只有一个 PDFView，所以没问题；一改成多窗口就变成：

```
打开 A → attach(A)
打开 B → attach(B)（把 A 顶掉）
切回 A → 事件进来，`event.window === pdfView.window` 不成立 → 什么都不做
```

**⇒ 已经改成"按 PDFView 各记一份"**（`sessions: [ObjectIdentifier: Session]`）：
监听器仍然是 app 级的一份，分的是每个视图自己的状态、以及"这个事件该交给谁"。
`attach` 幂等不清状态（否则按住空格时切窗口会断），`detach(from:)` 必须指名卸哪个
（原来的是无参 `detach()`，关一个窗口会把所有窗口那份一起摘掉）。
⌥滚轮的缩放回调也从单例属性改成 `attach(to:onZoom:)` 一起传，否则 A 的缩放
会写到 B 的工具栏百分比上。

### 二、`view.window` 在"下一轮主队列"里可能是 nil

`NSViewRepresentable` 里想拿"我在哪个窗口"的常见写法：

```swift
DispatchQueue.main.async { register(view.window) }   // ← 偶尔 window 还是 nil
```

实测会**静默失效**，而且症状看着毫不相关：窗口标题不更新（标签栏上显示成 "PDFReader"）、
不并进标签栏、**关闭确认代理装不上**。改成覆盖 `viewDidMoveToWindow()` ——
AppKit 给这件事的确定时机。

> 判断口诀：凡是"等下一轮主队列再取某个东西"的写法，都要问一句"那一轮它一定就绪了吗"。

### 三、同窗口的浮层会绕过 `event.window === pdfView.window` 那道过滤（v1.3.44）

上面两个全局监听器（空格拖拽 / ⌥+滚轮缩放）原来靠 `event.window === pdfView.window`
过滤，是为了不误伤 sheet / 设置窗口 —— 那些是**另外的窗口**。
而「页面管理」浮层从 `.sheet` 改成**同一个窗口里的一层普通视图**之后，这道判断失效了：

- 空格 + 拖动 → **底下的 PDF 真的被滚了**（用户看不见，关掉浮层才发现跑偏）
- ⌥ + 滚轮 → **底下的 PDF 真的被缩放了**
- 键盘监听 → ⌫ 会把底下的批注删掉

现在三个都显式问一句 `AppModelBridge.isPageManagerVisible(for: event.window)`
（按窗口查，因为是多窗口），盖着就**返回原事件放行**，让浮层自己处理。

## 页面管理：平铺所有页 · 多选 · 调序 · 删除 · 插空白页 · 可撤销（v1.3.42）

**⌥⌘P**（或缩略图面板右下角的按钮）打开。它是**盖在整个内容区上的浮层**
（v1.3.43 从 sheet 改过来、v1.3.44 提到 `ContentView` 最外层）：

- 用 sheet 尺寸会被父窗口卡着盖不满，而且是模态的、开着连窗口都关不掉；
- v1.3.43 挂在 `PDFContentView` 里，只盖住了 PDF 那一块 —— 顶栏和侧边栏还露着。
  现在从最外层 `ZStack` 铺满，**只留窗口标题栏**（macOS 的系统标签页长在那儿，
  多文件靠它切换，挡了就没法切文件了）。

- 网格平铺，缩略图下面写页码，当前页挂「当前」角标；格子 210~360、请求尺寸 560×780
- **点击**选中 / **⌘·⇧ 点击**多选（⇧ 是区间）/ **双击**跳到该页并关掉面板
- **拖动缩略图**调顺序（左半边＝插到它前面，右半边＝插到它后面，拖到网格**下方空白**＝排到最后）
- **⌫** 或工具栏「删除」；「移到最前 / 移到最后」是精确版的拖拽
- **「空白页」菜单**：在选中页之后 / 文档开头 / 文档末尾插入 1、2、5、10 页空白页
  （`⌥⇧⌘P` 插在当前页之后）。**纸张尺寸跟随相邻那一页**，插完自动选中新页
- ⌘Z / ⇧⌘Z 撤销重做（页面增删改都在同一条撤销链上）；**Esc** 也能关面板
- 只读模式下只能浏览，顶部有「进入编辑模式」按钮

### ⚠️ 拖拽落点：缝归最近的格子，兜底只管网格下方

"拖到两页**中间**松手，那页跑到最后一页去了"—— 根因是兜底 `onDrop` 挂在
`ScrollView` 上，命中区是**整个滚动区域**，连格子之间的缝也算；而兜底的语义是
"追加到末尾"。（那个 `+` 徽标是 `onDrop(isTargeted:)` 默认提交的 **copy** 操作画的。）

现在：列间距 / 行间距设成 0，间距改由 cell 自己的 `padding(.horizontal, 9).padding(.vertical, 10)`
补出来 —— 这两个 padding 加在 `onDrop` **之内**，所以命中区从卡片边缘外扩到缝中央，
缝上松手就落到最近那一格，插入点正好是两者之间。**左右对称**，所以
`cellWidth / 2` 的左右半边判断不受影响。

兜底则改成网格下方一块独立的 `endDropZone`（`DropDelegate` 形式，显式
`DropProposal(operation: .move)`），落到它会显示「移到最后」。

### ⚠️ `PDFPage()` 新建出来没有页面尺寸

做"插入空白页"踩到的：`PDFPage()` 的 `bounds(for:)` 是空矩形，**必须自己设 `mediaBox`**
（`cropBox` 也一起设，它不会自动推导）。不设的话缩略图渲不出来、写进文件之后是坏页，
而且全程不报错。尺寸取相邻那一页的，没有就退化到 A4（595×842）。

### ⚠️ 一切按「页对象」定位，不按下标

这是修"点这页却选中了别的页 / 删除不知道删了哪页"的关键。两个原因叠在一起：
**闭包捕获了构造视图时的下标**（视图被复用时那个闭包是旧的），
以及 **`ForEach` 外面又套了一层 `.id(...)`**（跟 ForEach 自己的身份打架，视图会被整体搬走）。

现在 `ForEach` 的身份直接是页对象，回调里传的也是页对象，
**点击那一刻才问 `viewModel.pageIndex(of:)` 换算成下标**。落点提示、⇧ 区间锚点、
拖拽落点目标，全都一样。

> 口诀：位置会变、视图会被复用，**身份不会**。回调里不要捕获位置。

### ⚠️ 改的时候不刷新，关面板才刷新一次

改一次页序的收尾里 `reloadTOC` 在长目录的文档上要 70~240ms，而这些面板
**此刻全被浮层盖着、用户看不见**。所以页面管理期间只更新网格（`pageRevision`），
`reloadTOC` / `reloadAnnotations` / 重绘全攒着，关面板时统一做一次。
实测连续 15 次改动只刷新 1 次。另外"当前页被删了要跳转"也一起延后 ——
改一次跳一次会让滚动位置一直乱动。

### 撤销栈要能表达"页数变了"

原来的撤销是"按下标一对一换整页"，**表达不了页数变化**。现在 payload 分两种：

```swift
enum Payload {
    case pages([Int: PDFPage])   // 批注类改动：页号 → 整页副本，页序页数不变
    case order([PDFPage])        // 页序类改动：完整页序，**对象引用**（不是副本）
}
```

`.order` 存**对象引用**是关键：目录的跳转目标和书签都指着页对象，存副本的话撤回来
目录就跳不动了。重排时搬的也是同一个对象，所以**页面上的批注自动跟着走**。

### ⚠️ 两个必须知道的坑

**① `PDFDocument.index(for:)` 对"不在文档里的页"返回 `NSNotFound`。**
删掉一页之后，目录里指向它的条目就悬空了 —— 写入器的错误消息里本来有
`第 \(index + 1) 页不存在`，`NSNotFound + 1` **算术溢出 → SIGTRAP**，
也就是"删一页 → 保存 → 报错的时候把进程带走"。现在 `errorDescription` 里不做算术，
`index(for:)` 的返回值统一判范围。

**② 悬空的目录条目不能"整套不写"、也不能"静默跳过"。**
前者让整套目录都写不进文件；后者会**连同子树一起丢掉**（一份 3 条目的目录直接变成无目录）。
现在**钳到第 1 页**（和目录面板里悬空条目显示的页号一致），而且只钳"写进文件的那一份"——
内存里的目录不动，⌘Z 把页找回来之后目标照旧。

### 顺带修的一个老 bug

菜单命令走 `NotificationCenter` **广播**，而一个文件一个窗口之后，每个窗口都会收到一遍 ——
**⌘Z 会在所有打开的文件上各撤销一步**（⌘S 全存一遍、⌘P 弹一摞面板）。
现在每个 handler 前面都加了一道 `viewModel.isInActiveWindow` 过滤。

## 「打开文件」页：虚线拖拽框 + 最近打开的缩略图（v1.3.48）

没打开任何文件时显示的那一页，按参考图重做成三块：标题 → **虚线框**（拖文件进来、
或点里面的「选择文件」）→ **最近打开**（每项一张**首页缩略图** + 文件名，右上角
「清除最近」）。整页都是拖放目标，有文件拖上来时虚线框会高亮变色。

### ⚠️ 缩略图必须**后台渲染**

`PDFDocument(url:)` 要读整个文件、`thumbnail(of:for:)` 还要再渲染一页 ——
一份几十页的 PDF 实测几十到几百毫秒。放主线程就是"一打开 app 先卡一下"。
所以 `RecentThumbnailStore` 的做法是：**后台渲染 → 主线程只查缓存**；
还没好的那格显示 `ProgressView`，渲染完发一次 `objectWillChange` 让它自己刷新。
实测 4 张缩略图渲染期间主线程**一条慢轮次都没有**。

两个细节：

- **每张图都要 `startAccessingSecurityScopedResource()`** —— 沙箱里从安全作用域书签
  解析出来的 URL，**不 start 是读不到内容的**（能拿到路径，但 `PDFDocument(url:)`
  直接返回 nil）。症状就是缩略图永远出不来。
- **后台各开各的 `PDFDocument`**，不复用主线程当前打开的那份，不共享 PDFKit 对象。
  `NSImage` 过 `Sendable` 检查用一个 `@unchecked Sendable` 的小包装（只在后台造、
  到主线程用，中间不传递）。

「清除最近」会连缩略图缓存一起清（不然清空后再打开几个会看到旧图）；
每项右键还有「移除这一项」（单独清它那张）。

## 关闭窗口：**关完最后一个要自己退出**，别等 AppKit 那条通知（v1.3.49 → v1.3.50）

两次实跑日志把这条链路补全了。

**第一层（v1.3.49）：放行了，窗口却没关。**

```
windowShouldClose 被调用
    confirmClose：没有未保存的改动 → 直接放行
  → 全部通过，允许关窗口
（之后既没有 windowWillClose、也没有窗口注销；28 秒后用户又点了一次才关掉）
```

现在放行之后会回看一眼（0.5 秒），窗口还在就自己 `close()`。同时把窗口当时的状态
记一条（`放行：原 delegate（…）不参与判定 · key=… 标签数=… 标签栏=… edited=…
挂着的 sheet=…`）—— `attachedSheet` 那一项是"窗口关不掉"的经典原因。

> 顺带一个改动：**不再手动调原 delegate 的 `windowShouldClose`**。翻遍日志它每次都回
> "允许"（6/6），一次有用信息都没带回来；而"它回允许、我们也回 `true`、AppKit 却没关窗口"
> 那两次恰好都在它后面。文档窗口能不能关，判定权现在完全在 `confirmClose()` 手里。

**第二层（v1.3.50，关键）：程序化 `close()` 关掉最后一个窗口之后，
AppKit 那条「最后窗口关闭」通知**可能不来**。**

```
⚠️ 放行 0.5 秒后窗口还在 → 兜底自己 close()
windowWillClose：收尾 → 窗口注销：还剩 0 个文档窗口
   ← 就断在这儿：没有 applicationShouldTerminateAfterLastWindowClosed，也没有退出
```

于是 app 带着 **0 个窗口**活着：Dock 里还在、点它没反应、再打开文件也没反应 ——
用户说的"卡死"。对照同一份日志里"点红叉关掉最后一个窗口"那次：注销后 **62 毫秒**
就正常退出了。

→ 新增 `QuitWhenIdle`：**每次窗口关闭**都回看一眼，"真的一个文档窗口都不剩了"就
自己 `NSApp.terminate`。查两轮，并且用 `DocumentOpener.hasPendingOpens` 排除
"正在打开新文件"（那种情况是换一个窗口，不是要退出）。

> **对照实验**（`PDFREADER_AUTOTEST_HARD_CLOSE` + `PDFREADER_AUTOTEST_NO_LAST_WINDOW_QUIT`）：
> 摘掉兜底 → `exit=124`、日志断在 `窗口注销：还剩 0 个文档窗口`（和用户日志一模一样）；
> 有兜底 → 主动退出、`exit=0`。

### ⚠️ 换掉 `NSWindow.delegate` 就必须兜住"用通知投过来的回调"（v1.3.51）

**`NSWindow` 不是直接调 delegate 方法的** —— 它把一批窗口通知**注册到 delegate 对象上**，
对应关系按名字来：`NSWindowDidBecomeKeyNotification` → `windowDidBecomeKey:`。
注册的判定依据是 `setDelegate:` 那一刻的 `responds(to:)`。

于是"代理 delegate"这种写法有个隐蔽的坑：

1. 代理的 `responds(to:)` **转发了原 delegate 的答案** → AppKit 认为它会实现那些方法，
   于是**把代理注册成了观察者**；
2. 代理自己没实现它们，靠 `forwardingTarget(for:)` 转给原 delegate 顶上 —— 平时没事；
3. 原 delegate 一旦消失（它本来是 **weak**），转发目标变 nil；
4. **通知中心是直接 `objc_msgSend` 发的，不会先问 `responds(to:)`** →
   `doesNotRecognizeSelector` → **整个 app 崩掉**。

现场就是用户那次「点系统标签栏，程序就死了」：

```
-[PDFReader.WindowCloseGuard windowDidBecomeKey:]: unrecognized selector sent to instance
  NSWindow becomeKeyWindow → postNotificationName → 观察者 → 崩
```

**两条走不通的路**：把这批方法一个个写出来（按公开通知名写全 25 个之后，又崩在
`windowDidOrderOffScreen:` —— 那个名字在 AppKit 头文件里 grep 不到，是内部通知，**枚举是打地鼠**）；
用 `methodSignatureForSelector:` + `forwardInvocation:` 兜底（**Swift 里写不了**，
`NSInvocation` 被标成 unavailable）。

**最终做法**：`+resolveInstanceMethod:` 里用 `class_addMethod` + `imp_implementationWithBlock`
**按需补一个转发实现** —— 只管名字形如 `windowDid…:` / `windowWill…:`（恰好一个冒号）的
"通知镜像"，原 delegate 能处理就转过去、处理不了就什么都不做。补进去的 IMP 由运行时缓存，
**不用枚举**，以后 AppKit 再加新窗口通知也不会崩。同时把原 delegate 改成**强引用**
（并在 `windowWillClose` 下一轮主队列里把代理从注册表摘掉，免得扣住窗口不还）。

> 验证：探针 `tools/probes/windowdelegateprobe.swift`（9/9，最后一段故意崩掉复现现场）
> ＋真 app 对照实验 `PDFREADER_AUTOTEST_KEY_NOTIFY`：
> 关掉兜底 → `exit=134` 且崩溃消息和用户贴的**一字不差**；有兜底 → `exit=0`。

### 右键「打开方式」会多一个空窗口（v1.3.50）

冷启动时 SwiftUI 会为"外部要求打开文档"**额外建一个窗口**，加上 `WindowGroup`
自己的启动窗口 —— 一个文件两个窗口，多出来的那个空着。`application(_:open:)`
改走 `DocumentOpener.openExternally(_:)`：只有"发起时所有窗口都是空的"才在 1.5 秒后
收掉多余的空窗口（这条判据排除了"用户自己按 ⌘T 开了空标签、随后又用 Finder 打开文件"
的情形）。

### 顺带：后台渲染 PDFKit 不能并发

同一份日志里还有 `慢轮次 2250ms / 2497ms · 活动=重载目录列表` —— 时间点和
"十来张缩略图**并发**渲染"完全重合。**PDFKit 内部有锁**，而主线程那边
（打开文件、`reloadTOC`、绘制）用的也是它，一堆后台任务会把主线程饿住。
改成串行队列 + 每张之间 `Thread.sleep(0.06)` 之后：缩略图变成一张接一张（间隔 ~100ms），
启动慢轮次 **2250ms → 182ms**。

> 口诀：只要主线程也在用同一个框架，后台任务就不能并发 —— 那不是"用满多核"，
> 是"跟主线程抢同一把锁"。

## 确认框要**挂窗口**，不要飘在屏幕上（v1.3.55）

杰哥的截图一张图里三个问题：

```
┌──────────────────┬───┐
│   （空白的白条）      │ + │   ← 窗口自己的系统标签栏，压在提示框上
├──────────────────┴───┤      而且那个 + 还能点（提示框正问着话）
│  [app 图标被切掉一半]      │
│  要保存对这份 PDF 的改动吗？ │
│  ☐ <Do not show this message a… │   ← 英文、被截断的复选框
```

### 根因：`alert.runModal()` 弹的是**独立窗口**

系统标签栏属于**窗口自己**，独立的 alert 窗口和它各画各的，位置一重叠就成了
"谁在上面看运气"。改成挂在**窗口上的 sheet**（`Utils/AlertPresenter.swift`）。

### 关键：**别在同步出口里等**（v1.3.55 的写法把 app 卡死了）

第一版为了同时满足"sheet 外观"和"同步拿答案"，写成了
`beginSheet` + `NSApp.runModal(for:)`。杰哥实测：**点完「不保存」，窗口关不掉、app 卡住**。
—— 在 AppKit 正处理"关闭"的路上又开一个 modal session，两套状态机互相等。

正确做法是**用两个出口各自给的异步路子**：

| 出口 | 先回什么 | 问完之后 |
|---|---|---|
| `windowShouldClose(_:)` | 回 `false`（**这次先别关**） | 自己再 `performClose` 走一遍 |
| `applicationShouldTerminate` | 回 `.terminateCancel`（**先退出流程**） | `NSApp.terminate(nil)` 重新发起 |

> ⚠️ `applicationShouldTerminate` 这里**不用** `.terminateLater`：那条路要求稍后
> `reply(toApplicationShouldTerminate:)`，而**退出挂起状态下 sheet 根本挂不上** ——
> 实测 `beginSheetModal` 调了、弹框却没显示，app 永远停在"正在退出"上。
> 用 `.terminateCancel` 退出来再重新发起，和 `windowShouldClose` 那边是同一个套路。

重复进入不会重复弹框：用户的答复会清掉脏标记（「不保存」清、保存成功也算清），
第二遍 `needsCloseConfirmation` 自然是 false。

### 还有两个坑（不加就白干）

1. **必须用 `alert.beginSheetModal(for:)`**，不能自己 `window.beginSheet(alert.window)`。
   自己挂的话，用户点按钮时 NSAlert 走的是它自己的收尾（`stopModal`），
   **不会** `endSheet` —— 我们传进 `beginSheet` 的 completionHandler **永远不会被调用**。
   现象：日志停在"问完了，都同意 → 重新走一遍关闭"，然后就没有然后了。
2. **`performClose` 要等 sheet 真的收干净**。`beginSheetModal` 的回调是在
   **用户点完按钮**就来的，那一刻 sheet 还在走关闭动画、`window.attachedSheet` 仍非 nil，
   此时调 `performClose` 会被 AppKit **直接忽略**。
   `WindowCloseGuard.closeAfterSheetDismissed` 负责等这一下（轮询到 `attachedSheet == nil`）。

### 三个具体的小毛病（都靠 dump 视图树查出来的）

1. **`alert.showsSuppressionButton = false` 这版 macOS 上没用** ——
   "不再显示此消息"复选框照样画出来，文案还是未本地化的英文。
   现场光看截图猜不出它是谁，于是加了个探针钩子（`PDFREADER_AUTOTEST_DUMP_ALERT=1`）
   把 alert 的视图树打进日志：

   ```
   _NSAlertContentView 0,0 260×328
     NSButton 20,147 218×18 hidden=false title=「<Do not show this message again>」
     _NSAlertButton 10,94 240×40 title=「保存」
   ```

   —— 既然就挂在 alert 的视图树上，那就**窗口建好后按文案找出来 `isHidden = true`**。
   对"要不要保存"这种框，**让用户能永久跳过是危险的**（勾一次以后改动全悄悄丢），
   想要这个效果的人应该去设置里关「关闭时提醒」。
2. **`alert.window` 不会按内容自动排版** —— 拿到就 `beginSheet` 会卡在初始尺寸，
   标题和正文各只剩**一行**（`NSTextField 220×16`）、长一点就截断。
   补一句 `alert.layout()` + `sheet.layoutIfNeeded()` 才正确（正文变成 4 行）。
3. **长文案放 `informativeText`，别放 `messageText`** —— 这版 alert 是一张 **260pt 宽的
   窄卡片、标题只排一行**，塞文件名进去必然截断成「要保存对「unsaved-test.」。
   正文会自动换行、要几行给几行。

### 怎么验的（这类 bug 只能"真的点一下"）

`PDFREADER_AUTOTEST_ALERT_CHOICE=0|1|2` 会让 app 自己等人点
「保存 / 不保存 / 取消」（按钮**按标题找**，因为视图树里的顺序和 `addButton`
的添加顺序不一样）。判据是**进程能不能自己退出**：

| 场景 | 期望 | 实测 |
|---|---|---|
| 关窗口 + 点「不保存」 | 窗口关掉、app 退出 | `exit=0` ✅ |
| 关窗口 + 点「取消」 | 窗口留着、app 继续跑 | 窗口保留 ✅ |
| ⌘Q + 点「不保存」 | app 退出 | `exit=0` ✅ |

修复前同样的场景是 `exit=124`（40 秒超时被杀 —— 就是用户说的"卡着了"）。

### 弹框上那条「选项条 + `+`」（v1.3.58）

用户第二次反馈："这个弹框**上面出现一个选项条和 `+` 按钮**。"

一开始以为是文档窗口自己的系统标签栏被 sheet 挤在了一块（还试过"弹框期间把标签栏藏起来"）——
**方向错了**。真正的原因在 `dumpWindows` 的输出里一眼可见：

```
窗口「」 是文档窗口=false
tabbingIdentifier=_NSAlertPanel-PDFReaderApp.WindowCloseGuard-(null)-HT-   标签栏=显示
```

**那是 `NSAlert` 自己的窗口**，而它的 `tabbingIdentifier` 里赫然写着
**`PDFReaderApp.WindowCloseGuard`** —— 我们的关闭确认代理**被装到了 alert 面板上**，
顺带改掉了它的 `tabbingIdentifier`，系统于是认为"这个窗口也参与自动标签页"，
**给确认框画了一条标签栏 + `+` 按钮**（用户点那个 `+` 真能开新标签，
正是因为我们的代理把 `newWindowForTab` 也接上了）。

`WindowCloseGuardInstaller.install` 原来的注释写着"面板、弹出窗不该拦"，
但代码里**只检查了 `.titled` 和 `isVisible`** —— 注释和实现不符，就是漏在这。

修两处：

1. `install` 里排除面板 —— `!(window is NSPanel)`, `window.level == .normal`（根因）；
2. `AlertPresenter` 里给弹框钉死 `tabbingIdentifier = ""` + `tabbingMode = .disallowed`
   （**两条都要**：只设 `tabbingMode` 实测不管用，系统照样给它画）。

> 教训：**改别人的窗口属性要付代价**。我们只是换了个 `delegate`，
> 系统却据此把窗口的"标签页身份"也改了 —— 这类副作用只能靠 dump 出实际状态才看得见。

## 沙箱与文件访问

开启沙箱后，文件访问有三个必须遵守的点，代码里都已处理：

1. **取得作用域的时机是"读文件之前"，而不是"创建标签时"。**
   `AppViewModel.addDocument` 先 `startAccessingSecurityScopedResource()`，再 `PDFDocument(url:)`，
   最后把"是否持有作用域"传给 `DocumentTab`，关闭标签时释放。
   **顺序错了会静默失败** —— 从「最近打开」恢复的 URL 没有作用域就读不到内容，
   `PDFDocument(url:)` 直接返回 nil，表现就是「点了没反应」。
   （从打开面板/拖拽进来的文件由系统临时授权，所以这条错了也看不出来，只有「最近打开」会暴露。）
2. **生成书签必须持有作用域。** 在作用域外生成的书签，下次启动能解析出路径、却读不到内容。
3. **书签有两种，解析方式不能混用。** 沙箱 `.app`（有 `app-scope` 权限）生成的是**带安全作用域**的；
   非沙箱构建生成的是**普通书签**。用 `.withSecurityScope` 去解析普通书签会直接失败。
   代码先按带作用域解析、失败再按普通解析，所以两种构建都能用。
   > 非沙箱构建下 `bookmarkData(options: .withSecurityScope)` 会抛
   > `Required entitlement com.apple.security.files.bookmarks.app-scope is missing or false`——
   > 这是正常的，代码会自动降级为普通书签，不会静默丢数据。

**打开失败时会弹提示**，而不是静默返回 —— 静默失败会让用户以为「点了没反应」，
也不知道下一步该做什么。

> 想先不带沙箱跑：把 `PDFReader.entitlements` 里的 `com.apple.security.app-sandbox` 改成 `<false/>` 即可，
> 其余都不用动（书签会自动走降级的普通书签路径）。

> ⚠️ **升级提示**：从 SPM 可执行文件（无 bundle id）切到 `.app`（bundle id `com.jiejie.pdfreader`）后，
> `UserDefaults` 换到了新域，**书签、最近打开、阅读进度会看起来被重置**。
> 旧数据仍在原域里没丢，需要的话可以写一次性的迁移（把旧域的几个 key 拷到新域）。

## 已知限制与后续

- **Bundle ID 是占位的**：当前为 `com.jiejie.pdfreader`，发布前改成你自己的域名反写。
  改动后同步更新 `tools/generate_xcodeproj.rb` 里的 `BUNDLE_ID` 并重新生成工程。
- **`.xcodeproj` 构建未在本机验证**：本次是在受限沙箱环境里工作，
  该环境禁止施加限制性沙箱 profile（`sandbox-exec: sandbox_apply: Operation not permitted`），
  导致编译器的宏插件服务被杀、`@State` 等宏无法展开。
  连一个 4 行的 SwiftUI 文件都会同样失败，与本工程无关 —— **在正常的 Xcode / 终端里可以正常构建**。
  代码本身已通过 `swift build -c debug/release` 全量验证（零错误零警告）。
- **`performSearch` 在后台队列调用 `PDFDocument.findString`**：PDFKit 并非线程安全，
  主线程同时渲染同一份文档时存在潜在崩溃风险，待定是否改回主线程。
- **自动滚动依赖 PDFView 内部的 `NSScrollView`**：PDFKit 未公开该视图，代码用递归查找，
  找不到时退化为主线程定时翻页。
- **代码签名是 ad-hoc（`CODE_SIGN_IDENTITY = "-"`）**：本机开发够用，
  准备分发时要换成真实开发者证书，并开启 `ENABLE_HARDENED_RUNTIME`。
- **批注拖动只改位置、不改大小**：目前没有缩放手柄。要加缩放就得同时改 `bounds` 尺寸
  并重算笔迹（因为笔迹路径不随 bounds 缩放，实测确认），工作量不小。
- **拖动只限在批注所在页内**：不跨页 —— 跨页需要把批注从一页摘下来挂到另一页，语义复杂且容易丢。
- **旋转过的页面未验证自绘**：`drawPagePost` 给的 context 在页面旋转时是否仍为未旋转的页坐标，
  没有实测过（手上的样本都是 0 旋转）。打开带旋转的 PDF 时若批注位置不对，是这里的问题。
- **我们创建的自由文本批注是纯文本**：自绘 `FreeText` 时按纯文本 + 系统字体渲染，
  **别的应用创建的富文本批注（带字体/颜色变化）会丢失排版细节**（内容不丢）。
  要更保守的话，可以在 `AnnotationRenderer.isSelfRendered` 里对带 `/RC` 的 FreeText 交回 PDFKit。

### ⚠️ 涂鸦（ink）的 `/Rect` 必须包住墨迹（v1.3.11 修的，会把文件写坏）

PDF 里 ink 批注有**两份几何**：`/InkList`（墨迹，**默认用户空间 = 页坐标**的绝对值）和
`/Rect`（批注矩形，代码里的 `bounds`）。规范要求 `/Rect` **包住** `/InkList`，
阅读器也会按 `/Rect` **裁剪**。

**而 PDFKit 改 `bounds` 时不会动墨迹。** 实测（线宽 6 的一条笔画）：

| 操作 | `/Rect` | `/InkList` |
|------|---------|-----------|
| 画完就存 | 77…203 / 117…163 | 80…200 / 120…160 ✅ 一致 |
| 再把 bounds 平移 (60,−25) | **137…263 / 92…138** | **80…200 / 120…160 一个数都没变** ❌ |

于是墨迹伸出 `/Rect`，**别的阅读器（预览……）就把露在外面的部分裁掉**。
Symptom 是"我们这边好好的，用预览打开少一块"——因为**自绘看不出来**：
自绘是 `paths（相对 bounds 原点）+ bounds.origin`，一减一加正好抵消，屏幕上始终完整。
（用户那份文件实测：`/Rect` 139.8…350.2，`/InkList` 58.1…259.5，**左侧伸出 81.7 点**。）

对照实验（真实窗口 + 合成事件，走完整的 `mouseDown → 拖 → mouseUp`）：

| 条件 | 写盘 `/Rect` | 写盘 `/InkList` | 结果 |
|------|-------------|----------------|------|
| 不重建笔迹 | 233.8 224.6 422.8 413.6 | x **200…380（没动）** | 左溢出 33.8、下 14.6 ❌ 会被裁 |
| **重建**（现在的做法） | 同上 | x **238.3…418.3（跟着走）** | 四边各留 4.5 = 半线宽 ✅ |

**两个对策（都在用）**

1. `AnnotationRenderer.reanchorInkStrokes` —— 拖动时把笔迹 `remove` + `add` 一遍，
   迫使 PDFKit 按**当前** `bounds.origin` 重新锚定，墨迹就真的跟着走了。
   > ⚠️ **不要把笔迹坐标再平移一次** —— 和箭头 `startPoint` 那个坑同源，
   > 多平移一次就是移动两倍（实测：正确 140…260，多平移会变成 200…320）。
   > 成本实测：500 点 0.7 ms、1000 点 1.4 ms、4000 点 5 ms；超过 2000 点降级为"松手时补一次"。
2. `AnnotationRenderer.reconcileInkBounds` —— 把 `/Rect` 校正到"包住墨迹"。
   在**打开后**（`applyDisplayPolicyToDocument`）、**写盘前**（`saveAnnotationsToDisk`）、
   **打印前**（`forceAnnotationsVisible`）各跑一次：既救回已被写坏的老文件，
   也保证任何遗漏的操作路径都不会再写出坏文件。**改的是框、不是墨迹**。

> 副作用（无感）：改过 `/Rect` 的 ink，PDFKit 会丢弃它原来生成的外观流，
> 于是外观改由阅读器按 `/InkList` 现生成 —— 位置和形状都对，只是不再复用缓存。
> 另外 PDFKit 自己生成外观流时会**再内缩 1 点**当裁剪边（实测），
> 所以描边最外缘那 1 点本来就会被吃掉一点点。

### 为什么"自绘"和"预览"看起来总会有点不一样（其它已知项）

自绘是为了清晰（PDFKit 的批注层 `contentsScale` 是 1.0，1x 栅格化再放大必然发虚），
代价是"我们画的"和"阅读器按文件画的"是两套渲染，观感差异集中在：

| 项 | 差异 | 说明 |
|----|------|------|
| 高亮 / 下划线 / 删除线 | 颜色深浅 | 阅读器对高亮常用 **Multiply** 混合，我们是 alpha 覆盖 |
| 矩形 / 圆 | 描边位置差**半个线宽** | 我们不再内缩（为了跟手，见 v1.3.10），PDFKit 是压在 `bounds` 内侧 |
| 文本注释 | **字体族可能不同** | 我们自绘用自己的字体；别的阅读器按 `/DA` / 自生成外观渲染 |
| 涂鸦 | 见上面一节 | 曾经会被裁掉一块，v1.3.11 已修 |
| 线条 / 箭头 | **箭头形状不一样** | 我们自绘是**倒钩 + 一体化轮廓**（v1.3.14）；别家按 `/LE` 画**平底三角**，而且线条画到端点再叠三角 |
| 半透明箭头 | **三角上会透出一条深带** | 阅读器把线条一直画到端点、再叠上三角；半透明时重叠处更浓（实测 α0.48 叠成 0.72）。我们自绘是**一次填充**、没有这条带（v1.3.14） |

**这些是"可接受的观感差异"；而 ink 被裁属于"内容丢失"，性质不同，所以单独修。**
